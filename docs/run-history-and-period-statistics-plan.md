# 单次运行、长期历史、周期统计与曲线查询方案

> 2026-10-23更新：最新[上行历史与页面数据方案](realtime-upward-history-and-detail-plan.md)规定上行归档、下行仅异常事件，并按附件补充“高度—拉力”平均曲线。本文原先的双向逐帧保存、完整往返记录、完成次数按结束日归属及仅时间桶曲线属于前一版建议，冲突处以新方案为准；可靠保存和自然日历原则继续参考。

本文件是方案，不修改生产代码、数据库或点位配置。延续已确认范围：单PLC、四机八索；大厅加清洗、命令、安全、统计四个业务服务；系统状态和单次清洗过程由清洗模块维护，统计模块负责历史保存与统计。没有数据过期判断，也不猜测未确认的PLC点位含义。

## 1. 当前实现与需要补齐的部分

| 当前内容 | 已有行为 | 尚不能解决的问题 |
|---|---|---|
| `PlcMessageBuffer` | 同一设备只保留尚未消费的最新快照 | 较早快照可能被覆盖，不能作为逐帧历史来源 |
| `SampleStatistics` | 内存累计有效样本，返回`PROCESS`范围统计 | 重启消失，不是日/月/季度/半年/年统计 |
| `TelemetryHistoryBuffer` | 最多2048个已整理批次的内存队列 | 不是2048帧；没有断电恢复，满队列时不能继续可靠保存 |
| `HistoryBatchPersistence` | 每轮取最多20个批次，失败时回队 | 回队期间新批次可能占满容量；回队本身也可能失败 |
| `JdbcTelemetryHistoryDao` | 批次、分段、测点汇总事务保存，以批次标识去重 | 没有单次运行全过程采样；分段最小/最大/平均值无法还原原始曲线 |
| 现有历史查询 | 按范围最多读取5000个分段，并逐段查询测点 | 固定截断不是完整分页，存在大量附加查询，不适合作为新历史页面契约 |
| 生产采集与历史任务 | 尚未生成单次运行/历史批次，历史保存默认关闭 | 不能将表和DAO存在解释为已可靠保存每次运行 |

现有7表是当前基线。下面的数据对象和索引属于拟议设计；实施时需审阅迁移关系，不能把新建表脚本当作旧库升级，也不能先删除旧数据。

## 2. 数据分成五类，原始历史持续保留

| 拟议数据对象 | 保存内容 | 主要用途 |
|---|---|---|
| 单次运行记录 | `runId`、设备、已确认开始/结束时间、首次/最后观测时间、结果/终止原因、参数快照、统计摘要、数据缺口说明、可验证的操作来源 | 运行列表和单次详情 |
| 核心采样帧 | 唯一采样标识、设备、采集时间、入库时间、可空的`runId`、八索拉力、四机高度/速度/力矩相关值、同步速度、必要状态、通道有效性、换算所需原值/映射版本 | 原始曲线、重算和追溯 |
| 事件 | 唯一事件标识、设备/运行、发生或观测时间、故障/急停/中断/恢复/通信失败及恢复/后台操作、具体原因 | 解释曲线变化和数据缺口 |
| 周期统计 | 周期类型、起止时间、运行次数/结果分布、已知运行时长、异常摘要、各测量的有效数量/和/最小/最大、计算版本、已纳入数据位置 | 日、月、季度、半年、年报表 |
| 曲线汇总桶 | 时间桶、测量项/通道、有效数量/和/最小/最大、极值时间、首末有效值、缺口信息 | 有界的数据量展示长时间曲线 |

四机八索固定规模，核心采样建议一帧一行，使用固定测量列与有效性标记；不把每个点都拆成一张表。没有自动清洗归属的采样，其`runId`可空，不能冒充自动运行。

周期统计和曲线桶是另外保存的派生结果，不覆盖原始采样，不把一条运行记录改成一条“月记录”，也不为每个统计周期复制一遍原始采样。

后台操作账号来自登录身份；PLC现场启动没有可验证后台操作者时，记录现场来源，操作人留空。

## 3. 一次运行如何入库

1. 清洗服务依据已确认的实际开始事实分配`runId`，保存进行中的运行记录。开始判定不在本方案中新增未确认的点位组合。
2. 运行中持续将采样和事件关联到该`runId`，以短事务分批入库，不等整次结束，也不使用覆盖整次运行的大事务。
3. 临时停止、已确认的中转、异常回退先记录过程事实。只有明确退出本次运行时才结束记录，不因任意一次故障信号就拆出新运行。
4. 明确正常完成时更新结束时间、结果和摘要；明确中断/故障结束时保留实际原因，不混入正常完成次数。
5. 服务中途接入、通信中断或重启后无法确认边界的，保留实际采样和已知关联，标明开始/结果未确认。不能虚构开始时刻，也不能补算完整往返次数。

实际观测到的M8可作为正常回原位的依据；其约1秒脉冲可能漏采，当前点位条件不能保证完整识别每一轮。M9仅为下降到位。未知周期含义不纳入设计。

服务重启时，从已经提交的运行状态和待处理记录恢复，再按原有标识重放；运行状态检查点与相应数据需保持一致。无法确定断线期间发生过什么，就保留未确认结果，不能以重启直接判定正常完成。

## 4. 时间范围统一采用业务时区与左闭右开

建议业务日历沿用项目已配置的`Asia/Shanghai`。数据库保存统一时间点；接口以带时区时间表达。划分周期前先按业务时区计算边界，不能直接用服务器UTC的日期代替业务日期。

以2026年10月22日为例：

| 周期 | 包含起点 | 不包含终点 |
|---|---|---|
| 当日 | 2026-10-22 00:00:00 | 2026-10-23 00:00:00 |
| 当月 | 2026-10-01 00:00:00 | 2026-11-01 00:00:00 |
| 当季，第四季度 | 2026-10-01 00:00:00 | 2027-01-01 00:00:00 |
| 本半年，下半年 | 2026-07-01 00:00:00 | 2027-01-01 00:00:00 |
| 当年 | 2026-01-01 00:00:00 | 2027-01-01 00:00:00 |

自然月不是固定30天。季度为1—3、4—6、7—9、10—12月；半年为1—6、7—12月；自然年为当年1月1日至次年1月1日。闰年与月末由日期规则处理。“最近30天/半年/一年”如以后需要，应使用独立的滚动范围，不混用这些自然周期名称。

界面可以写“00:00:00—23:59:59”，查询条件必须是“大于等于当日零点、小于次日零点”，这样不会漏掉23:59:59之后的毫秒数据，也不会重复计算次日零点。

本日、本月等尚未结束的周期，只累计已经收到并保存的数据，标记为进行中；未来时间不补0。展示已统计到的位置属于结果说明，不是数据过期判断。

## 5. 跨天、计数和平均值的口径

| 指标 | 方案口径 |
|---|---|
| 启动次数 | 真实开始时间所在的日期计一次；开始时间未知的不补入 |
| 正常完成次数 | 明确正常结束时间所在日期计一次，不按跨越日期重复计数 |
| 中断/故障结束次数 | 明确退出本次运行的时间所在日期计一次，并区分原因 |
| 运行列表筛选 | 默认按开始时间；查询与某日有重叠的运行时，必须明确使用另一筛选口径 |
| 运行时长 | 按清洗服务已经确认的运行区间与统计周期的交集累计；运动时长如需要，应另设口径 |
| 测量统计 | 按实际采集时间归属对应时间桶和日期，不按补传入库日期归属 |
| 故障事件数 | 按故障事件发生或首次观测日期计数；持续高电平不每帧重复计事件 |
| 异常时长 | 有可靠起止才累计；跨天拆分，同类重叠区间按并集处理；通信未知区间不算成正常 |

例如一次运行在10月22日23:58开始、10月23日00:08正常结束：22日启动1次，23日正常完成1次；若这十分钟都是已确认运行区间，则分别分配2分钟、8分钟运行时长。运行表仍然只有一条。

每个测量项和通道保存`sum、validCount、min、max`。周期采样平均值由`sum/validCount`计算；月平均不能直接平均每日平均，全年也不能直接平均每月平均。这里得到的是有效采样平均，不冒充时间加权平均。

无有效测量时平均/极值为无数据。明确观察到零次完成与缺少数据无法确认次数，界面必须能区分。

## 6. 历史统计预先计算并持久保存

周期统计采用同一结构，`periodType`区分日、月、季度、半年、年。每个设备和周期边界只有一个有效结果版本，避免为五类周期各建一套业务表和算法。

后台计算流程：

1. 采样、事件、运行结果提交数据库时，同时留下受影响时间段的待更新标记。标记也必须持久化，避免服务重启后漏算。
2. 统计服务后台更新已变化的短时间桶和当日结果；例如每分钟更新当前快照。这是可调任务频率，不是点位过期规则。
3. 相应结果变化后，更新受影响的月、季度、半年和年；可由日汇总或月汇总组合，不能混合重叠来源重复计算。
4. 跨日后自动完成上一日汇总；月末等周期结束时生成已结束周期的保存结果，不等用户第一次查询才生成。
5. 当前周期的快照也后台更新。用户请求只读已保存结果，不因查看当月就扫描全部原始历史。
6. 迟到、重试补入或修正的数据，按采集时间标记其所属历史日期，再重算受影响的上级周期。已结束不等于永远不允许修正。

日汇总与月汇总结合时，要分别处理运行计数、已确认时长、测量和/数量/极值，不能拿“单次运行均值”简单代替整月测量统计。

重算使用确定范围覆盖生成一个新版本，而非在重试时再次累加旧总数。读取源数据的版本与待更新标记关联；计算中又有补传，就继续保留待更新，避免旧计算结果覆盖新需求。失败保留任务重试，查询返回上一次成功版本并说明更新情况，不返回伪造0，也不触发全库扫描。

调度入口主动调用统计服务，统计服务委派计算器/保存器并调用DAO。DAO不通知清洗服务、统计服务等上层。

## 7. 缓冲、重试和数据传输异常

### 7.1 缓冲分工

| 缓冲 | 保存方式 | 规则 |
|---|---|---|
| 实时最新值 | 内存中每设备一份快照 | 可以覆盖，用于页面即时展示 |
| 历史待保存数据 | 持久磁盘待处理记录，内存仅作为有界批处理窗口 | 不允许新帧覆盖尚未提交的旧帧，入库确认后才推进消费位置 |
| 统计待更新 | 数据库中的待更新标记/任务 | 合并相同时间段的工作，不丢失重算要求 |

项目中“回温缓冲”的注释目前只是失败回队，不能视为已经实现可靠持久缓冲。

可靠历史必须在快照可能被覆盖前分流：底层采集将每个成功取得的采样写入持久待处理区；上层PLC表示入口主动读取，再进入大厅、清洗编排、统计保存与DAO。底层只提供读取/确认能力，不反调业务服务。实时页面独立读取清洗服务的最新状态，慢用户不能堵住历史保存。

建议按小批量和最长等待时间共同触发入库，例如最多200帧或等待1秒就提交一批，实际值压测后确定；这与统计任务每分钟更新的频率不同，也不代表等一轮结束再存。

### 7.2 事务和去重

- 给每个已采集的数据项稳定标识，可由设备、采集实例标识和该实例内序号组成。采集实例标识跨重启不复用，重放仍沿用原标识；批次和事件也具有稳定标识。
- 数据库事务提交本批采样、关联事件/运行变更和待统计标记。提交成功后才确认消费持久待处理记录；崩溃后允许重放，由唯一约束防止重复入库。
- 数据库已提交但响应丢失时，以相同标识重试。重复记录不能重复增加次数、时长或统计；标识相同但内容冲突必须暴露，不能用忽略所有插入错误来吞掉问题。
- 持久待处理区在数据真正刷新到可靠磁盘后才算接受。若使用批量刷盘，必须明确断电损失窗口，不能把内存写入成功描述为断电不丢。
- 已确认入库的缓冲文件可以回收；原始数据库历史继续保留。缓冲容量、数据库历史容量、备份容量分别规划。

### 7.3 异常处理

| 情况 | 处理 |
|---|---|
| PLC读取失败/通信断开 | 保存实际失败与恢复事实；未取得的采样不补造，曲线显示缺口 |
| 单通道值无效 | 保留帧和该通道有效性，其他有效通道继续保存；无效值不作为0参与统计 |
| 数据库暂时不可用 | 持久待处理记录继续积压；有上限地批处理和退避重试，实时/控制不能等待整批重试 |
| 重复数据或提交响应丢失 | 使用同一标识重试，数据库去重，统计从有效源数据生成 |
| 延迟到达的数据 | 保存原采集时间，修正其所属日期/周期，而非计入到达当天 |
| 服务重启 | 重放未确认记录，恢复已提交的运行检查点；无依据的运行边界保留未确认 |
| 汇总计算失败 | 保留原成功版本与待更新任务，修复后重算，不删除原始历史 |
| 持久缓冲磁盘满或损坏 | 明确显示历史保存失败并记录可观察的缺失情况；保证控制路径不等待无限重试，不宣称仍在可靠保存 |

持久缓冲解决的是已经采到、尚未入库的数据。后端或PLC停机期间从未采到的数据，当前没有已经确认的PLC历史补取能力，无法靠重试恢复。单一磁盘持久化也不等于备份；已入库历史和未确认缓冲均需考虑备份与恢复。

## 8. 曲线如何提供给前端

运行次数/时长报表和测量曲线使用不同数据源：报表读取周期统计；拉力、高度、速度等曲线按范围读取原始帧或曲线汇总桶。一个月平均值无法还原这个月的过程曲线。

曲线汇总可先保存5分钟、小时、日粒度的桶；必要时再扩展更细粒度。已完成的时间桶后台生成，当期桶后台更新，迟到数据只修正受影响桶。合并桶时组合和、有效数量和极值，不平均平均值。

| 页面/时间范围 | 推荐返回内容 |
|---|---|
| 单次运行 | 当前选中通道的原始帧；超过显示预算则降采样或使用合适汇总粒度，放大后读取局部细节 |
| 今日全天测量趋势 | 例如5分钟桶，完整24小时为288桶；今日只显示已采部分 |
| 历史整月测量趋势 | 例如小时桶，28—31天为672—744桶 |
| 季度/半年/全年测量趋势 | 例如日桶，按实际日历返回 |
| 月内每日运行次数/时长 | 28—31条日统计 |
| 全年每月运行次数/时长 | 12条月统计 |

每桶返回最小、最大、平均及有效数量；需要定位峰值时附极值时间，前端显示均值趋势和极值带，不能仅抽每N个点而隐藏峰值。通信缺口应单独返回明确区间，曲线在缺口断开，不能让跨缺口的桶或插值线冒充连续测量。

## 9. 查询契约和前端体验

以下为业务查询契约，不代表接口已实现：

| 查询 | 请求范围 | 后端返回 |
|---|---|---|
| 运行列表 | 设备、时间范围、结果、游标、页大小 | 例如每页20条，最大100条；仅记录摘要和下一页游标 |
| 单次详情 | 设备、`runId` | 单次参数、结果、摘要与缺口说明；事件另按页取，不内嵌全部采样 |
| 周期报表 | 设备、自然周期类型、日期 | 已保存统计结果，业务时区、边界、计算版本、进行中/已结束及更新情况 |
| 曲线 | 设备/运行、起止、测量项/通道、显示预算 | 服务端选择后的粒度、时间桶、必要缺口、单位和覆盖范围 |
| 事件列表 | 设备/运行、起止、游标 | 故障和操作时间轴，分页读取 |

曲线可设每序列最多800个桶、一次最多8条序列作为初始显示预算，最终上限由测量验证确定。后端强制控制返回规模；超预算时调整粒度并返回实际粒度，不能静默丢掉后半段。用户确需更细数据时缩小时间范围；大量导出采用独立后台任务。

默认先显示运行列表/统计卡片，再读取当前选中的图表。四机高度与八索拉力使用各自单位和图组，不把全部通道、全部历史塞进一个响应。切换时间和缩放图表时重新请求局部范围。

查询必须同时约束设备与时间，后端授权后访问DAO。运行列表使用稳定的时间与ID游标；采样至少支持“设备+采集时间”和“运行+采集时间”索引；周期统计按设备、周期类型、起点唯一定位；曲线桶按设备、测量/通道、粒度、时间查询。避免逐条查测点的附加查询，也不要求每次翻页都统计全表总行数。

## 10. 长期容量与实施顺序

单PLC先使用现有MySQL和持久磁盘缓冲，不把新消息中间件或时序库作为前置条件。若持续每秒2帧，365天约6307万帧；分区、索引、派生桶和备份也占空间。MySQL没有与本业务对应的固定“最多保存几条”，可用年限取决于实测每帧含索引大小、写入/查询性能和可用磁盘。

长期原始数据按时间组织，数据量验证后采用按月分区或独立归档存储，由后端按时间路由；不让前端自己选择物理表，也不为日/月/季/半年/年报表建立五份原始副本。采用分区或归档前必须同时审阅唯一键、外键与迁移限制。汇总保存在常用查询存储中，长期原始历史有可验证的读取与恢复路径，不自动删除。

建议按以下顺序实施，后一步不冒充前一步已完成：

1. 确认已经明确的单次运行边界，补齐稳定采样标识、覆盖前分流、持久缓冲、逐帧/事件/运行事务保存与重放。
2. 建立日历统计口径、持久待更新任务、五类周期预计算及迟到数据修正。
3. 建立曲线汇总桶、运行/事件分页、受限图表查询和前端缩放交互。
4. 使用代表性运行数据验证磁盘容量、写入、长历史查询与备份恢复，再确定分区/归档。

验收至少覆盖跨午夜、月末/闰年、故障未结束运行、重复提交、提交成功响应丢失、数据库中断后恢复、重启重放、历史补传重算、平均值合并和曲线缺口/峰值；确认全年报表读取汇总，不扫描全年原始采样。
