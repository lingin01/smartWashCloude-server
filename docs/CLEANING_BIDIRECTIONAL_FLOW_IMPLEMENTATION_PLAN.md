# 清洗盒子与云端双向消息流程实施计划

## 1. 本次目标和边界

先验证真实 MQTT 收发、队列消费、表示层转换、大厅分派及回执关联。具体拉力、速度、历史曲线字段后续完善，不把链路验证当作设备执行完成。

沿用现有目录、线程中心和消息对象，不另建一套 MQTT 服务。云端为主要修改项目；盒子仅补充联调标识转换和禁止执行的保护，不修改 PLC 控制、不编译盒子。

## 2. 按顺序实施

1. 保留默认正式模式：签名未就绪仍阻止设备控制下发。
2. 新增显式、默认关闭的链路验证配置，并限定允许联调的盒子编号。联调消息携带 `flowCheckOnly=true`，不伪造签名、不关闭用户鉴权。
3. 盒子 Converter 读取联调标识，随 Param 进入大厅；安全服务明确返回 `FLOW_CHECK_RECEIVED` 拒绝执行。现有命令回复队列发布回执。
4. 云端继续通过原命令队列、MQTT 服务发布，经接收队列、表示层、大厅关联 requestId。回执中的中文公共错误码优先于内部数字错误码。
5. 按当前盒子 Converter 修正配置消息的字段和单位映射：startTime、runIntervalMs、groupSpeedMetersPerMinute；只提供挡位但没有挡位—速度映射时明确拒绝，不猜测速度。
6. 使用本机真实 MQTT Broker 和 Paho 客户端验证上传和下发回执；模拟盒子客户端不执行设备动作。既有 HTTP/权限/队列测试继续回归。
7. 记录测试结果及现场操作步骤，明确现场盒子编译和联调仍由现场完成。

## 3. 验收流程

下发：HTTP → 表示层 DTO/Param → 大厅 → 安全/清洗 → 命令服务 → 协议消息 → 发送队列 → MQTT → 盒子接收队列 → Converter → 大厅 → 安全服务拒绝联调执行 → 命令回复队列 → MQTT → 云端接收队列 → 表示层 → 大厅 → 命令状态查询。

上传：盒子消息对象 → MQTT → 云端网络服务 → 接收缓冲 → 表示层 → 大厅 → 统计服务 → 热缓冲（实时）或温缓冲（历史）。数据库保存沿用现有后台任务，本次不启用建表或虚构数据库保存确认。

验收需观察匹配 requestId 的 `REJECTED/FLOW_CHECK_RECEIVED`，不能只看 Broker PUBACK。联调终态 REJECTED 表示有业务回复、未执行动作，不表示设备控制功能已经完成。

## 4. 不在本次完成的内容

正式签名、实际 PLC 配置写入及生效反馈的现场验证、完整历史字段和曲线、历史业务保存 ACK、命令持久化及重启恢复。当前盒子已有三参数写入/读回相关源码，旧交互文档对该部分的占位说明不能当作最新实现状态；本次不修改或验证 PLC 点位。真实盒子未连接时只报告本机协议测试结果，不宣称现场联调通过。

## 5. 执行记录

已实施：显式联调配置、白名单、无伪签名的协议封装、盒子联调标识解析与禁止动作保护、大厅保留公共说明、云端回执公共码解析、三参数协议对齐，以及本机 Broker/Paho 测试。测试结果见下节。

## 6. 现场联调步骤

1. 在现场编译本次盒子改动并部署。盒子业务 boxId、MQTT 订阅/发布路径中的编号和云端请求中的 boxId 必须一致；不能直接假设 clientId 等于业务 boxId。
2. 盒子与云端连接到同一个 Broker，确认盒子订阅 `/command/emergency-stop` 和 `/command/settings`，云端订阅 `/command/reply` 及遥测主题。保持 QoS 1、retained=false。
3. 云端启动参数显式添加 `--spring.profiles.active=dev,flow-check --cleaning.interaction.flow-check-box-ids=现场盒子编号`。多个白名单编号以英文逗号分隔。也可通过环境变量 CLEANING_FLOW_CHECK_BOX_IDS 提供白名单。默认启动不启用联调模式；空白名单或非白名单目标会被云端拒绝。
4. 使用已有用户登录取得 access token，提交以下 HTTP 请求；用户鉴权不关闭。用新的 requestId 标识每一次不同操作。

急停链路验证：`POST /api/cloud/cleaning/boxes/{boxId}/emergency-stop`

```json
{"requestId":"flow-stop-001","reason":"仅验证双向消息链路"}
```

配置链路验证：`PUT /api/cloud/cleaning/boxes/{boxId}/settings`

```json
{
  "requestId":"flow-settings-001",
  "expectedVersion":0,
  "settings":{"startTime":"08:30","intervalSeconds":60,"groupSpeedMetersPerMinute":0.8}
}
```

这些值仅供报文解析联调，不写入 PLC。实际配置版本及业务值应在后续正式联调时确定；本次没有把示例版本宣称为设备版本。

5. HTTP 首次返回 202 只表示入队。随后调用 `GET /api/cloud/cleaning/boxes/{boxId}/commands/{requestId}`，期望 `state=REJECTED`、`code=FLOW_CHECK_RECEIVED`，中文说明“消息已到达盒子业务入口，未执行设备操作”。正式配置查询仍与申请值分开，不能显示联调参数为生效值。
6. 上传可通过 `GET /api/cloud/cleaning/boxes/{boxId}/realtime` 检查热缓冲。历史数据进入温缓冲，现有历史持久化配置默认关闭；这不表示数据库已经保存，不能释放盒子待确认历史。
7. 完成后撤销 flow-check 启动 profile/参数，恢复默认模式。不要使用旧盒子构建作为联调保护已部署的证明；即使标识未被旧构建识别，也不能以旧版本当前拒绝签名作为长期保障。

## 7. 自动测试与验收限制

2026-10-07：Java 17 云端编译与 4 个测试类回归通过，共 18 项测试，失败 0、错误 0、跳过 0。包含 3 项新增 Broker/联调边界测试、11 项消息流程测试、3 项 HTTP 权限测试和 1 项服务启动上下文测试。首轮模拟客户端因订阅 `command/+` 收到自身回执导致断言失败，已修正为两个明确下行主题后完整回归通过。

`CleaningBrokerFlowTest` 使用 127.0.0.1 临时端口的真实 Moquette Broker、真实云端 Paho 传输及模拟盒子 Paho 客户端。验证实时上传到热缓冲并可查询、历史上传到温缓冲、急停/配置消息入队并到达对端、数字阶段回执和公共中文错误码关联查询。测试不运行 C++、不连接 PLC、不实际落库。

另外验证：默认正式模式仍阻止未签名下发、空/不匹配白名单拒绝、没有伪签名、秒到毫秒及 HH:mm 转换、不猜测挡位速度、间隔乘法溢出拒绝。既有消息流程、HTTP 权限及启动测试一并回归。

盒子离线契约源码已增加联调标识转换和安全服务拒绝用例，按用户要求本次未编译运行盒子。现场双端验收必须在部署盒子新构建后执行第 6 节步骤，不能以本机模拟对端测试替代。
