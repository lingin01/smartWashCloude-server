## 2. 当前最关键的缺口：运行与数据保存

当前实时入口主要走这条链路：

```text
PLC采集 → 转换最新快照 → 清洗服务状态 → 进程样本统计 / 实时查询与旧SSE
```

旧历史保存器能够处理外部交给它的历史批次，但生产代码中尚未形成下面的完整过程：

```text
采集事实 → 确认方向/用途/分段 → 识别生产上行记录及PLC异常过程
        → 原始采样与事件可靠接收 → DAO事务提交并确认
        → 历史列表 / 单次详情 → 日历及高度预计算 → 报表 / 导出
```

因此，仅打开`cleaning.history.persistence-enabled`不会自动得到一次清洗记录、原始曲线和历史统计；必须实现前面的业务整理和可靠接收。

[TelemetryHistoryBuffer](../src/main/java/com/company/project/info/buffer/cleaning/TelemetryHistoryBuffer.java)当前容量为**2048个历史批次**，它是内存队列，不是2048个原始采样点，也不是数据库容量。保存失败会把当前及未处理批次回队，回队遇满也会抛错；进程退出或断电后不能依靠该队列恢复。

需要补上的是持久待保存缓冲、稳定源标识、提交确认与重放、明确的满缓冲处理。目标是让已经可靠接收的数据能在重启后继续保存，重放不重复增加记录、事件、时长或统计值，而不是只让正常运行时的INSERT成功。

## 6. 建议实施顺序与交付标准

| 阶段 | 工作 | 阶段完成标准 |
|---|---|---|
| 1. 明确事实和接口保护 | 设备身份、新点位、必要PLC语义、目标DTO与资源授权 | 已确认采样可追溯，未知值如实表达；新增路径有实际鉴权 |
| 2. 可靠保存与运行/事件事实 | 目标表迁移、持久缓冲、运行/用途分段、PLC事件身份 | 一次已确认生产上行及相关异常可可靠保存，数据库失败/重启后能恢复已接收数据 |
| 3. 实时与历史展示 | 首页目标推送、详情、系统历史分页、日期目录与原始点表 | 一次记录可从列表进入详情，按实际来源查看全部已存点，页面不获取全库 |
| 4. 操作生效确认 | M50反馈、三参数与两路阈值saved/applied、命令查询 | 申请、写应答、实际生效清楚分开；失败/部分确认可追溯 |
| 5. 周期与导出 | 预计算、跨日/补数修正、归档比较、导出任务 | 已结束月份无需逐次重算原始数据，文件来自完整一致快照 |
| 6. 实测与验收 | 容量、性能、断联/断电/重启、备份恢复、真实PLC和页面联调 | 对已确认的业务范围形成可重复验证结果，保留数据缺口与未确认范围 |

这些是依赖顺序，不要求所有工作串行：权限可随每个接口同步完成，已明确的事件保存可以与运行保存并行。第一条应交付的完整业务流程是“PLC采集→一次生产上行及异常可靠保存→历史列表→单次详情”，不能用返回固定值的Controller代替它。

长期历史的容量需要按实际采样频率、UP时长、行宽/索引、事件量与备份占用测量；目前没有足够现场数据给出可信的“最多多少条或多少年”。永久保留目标需要容量规划与扩展支撑，不自动删除历史来掩盖不足，也不把Redis、Kafka、时序库作为这条首要流程的前置条件。

## 7. 本期不要求补齐的内容

远程启动、复位、解除急停、暂停/恢复、单轴升降属于已明确的未开放范围；不能因存在PLC内部点位就自动变成待上线按钮。视频不纳入本期，模型管理、历史巡检和独立数据分析仍是待开放/占位内容，不阻挡当前数据保存流程。

正常DOWN的连续历史、完整往返曲线和全程峰值不在当前归档范围。继续保留所有已选UP用途原始，默认生产统计仅PRODUCTION_UP，DOWN只留有限事件与有依据的过程峰值说明。前端模拟能画下降不代表后端已保存下降。

不增加采样时间年龄、过期或先后校验；去重与顺序依靠稳定源身份/序号，离线依靠实际通信事实。查询日期输入、会话有效期和事件版本控制分别处理，不能混称为采样过期检查。

前端附件报告的300项测试和9项浏览器模拟检查属于前端报告。本仓库已有通信、权限、分层、统计和推送等测试；完整生产历史、PLC事件、生效确认和现场恢复仍需要针对实际实现验收。
