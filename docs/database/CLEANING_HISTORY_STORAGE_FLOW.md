# 清洗历史数据存放流程说明

日期：2026-10-13。范围：盒子 iot_box_cleaning 与云端 SmartWashCloud-Server。

本文区分“已确定的业务口径”“当前代码已有路线”和“待实现的可靠闭环”。本次只编写文档，不修改代码、配置或数据库，不编译盒子，不连接 PLC。

共同协议以 [盒子对齐要求](../CLEANING_BOX_ALIGNMENT_REQUIREMENTS.md) 引用的盒子协议为准，表结构以 [基础表 V1](README.md) 为准。本文不另建协议版本、历史表或缓冲框架。

## 1. 存放的是什么

一个罐体对应一套清洗系统及一个盒子，盒子下面有四台绞机、八根索、八个拉力传感器，每台绞机对应两路拉力。

历史层次必须分开：

| 层次 | 一条记录的含义 | 关联关系 |
|---|---|---|
| 自动作业 session | 设置好后连续执行的一次自动作业，可跨日并包含多轮 | 一个 session 对应多轮 |
| 清洗轮次 round | 一次正常上下过程及其最终结果 | 属于原 session |
| 历史留点 record | 某轮在一个真实时间、真实高度保存的测量点 | 一个 round 有多个点 |
| 上传批次 batch | 为传输组织的一组历史记录 | 不等于作业或轮次，可包含不同轮次的记录 |
| 测量 measurement | 一个点中的某根索拉力、某台绞机速度等 | 一个点对应多路测量 |

PLC 自恢复往返仍属于原轮次，不额外算一轮。检修运行不进入自动清洗作业曲线及正常轮次统计。不能凭一批上传完成推断一次作业完成。

## 2. 500ms 采样与 0.5 米保存

500ms 是盒子与 PLC 的目标采样节奏，不是云端每条历史记录的时间间隔。当前调度及真实采样接入仍需核对，不能仅根据配置宣布全链路每 500ms 都有新数据。

第一阶段历史使用真实留点：

- 正常自动上行：以上一次普通高度留点为累计基准，移动约 0.5 米后保留当前真实帧。
- 不使用相邻两帧高度差作为累计基准，否则低速运行每帧都小于 0.5 米，可能一直不保存。
- 不虚构正好落在 0.5 米网格上的测量值；跳过网格时保存当前实际高度，不能插补为实测点。
- 首点、末点、阶段变化及重要事件额外保留，具体触发和事件重复去重需落实到盒子。
- 正常下行不进入常规上行曲线；下降异常、自恢复片段额外保存，并保留真实 UP/DOWN 方向。
- 无效高度不能用来触发普通高度留点；无效拉力、速度保存有效性及空值，不补零。

恢复期间系统仍正常、工作仍运行。连续五次未恢复且 PLC 确认最终失败后，才将该恢复判为故障；第五次成功不判故障。急停、设备离线和独立故障按自身规则处理，不都等待五次恢复。

异常片段的边界与现场恢复信号仍需确认。恢复成功后是否整轮排除正常统计，还是只排除恢复片段，仍是待确认策略，不在本次存储文档中擅自决定。

## 3. 热、温、冷各存什么

| 位置 | 保存内容 | 用途与限制 |
|---|---|---|
| 盒子热缓冲 | 最新实时快照 | 展示与实时上报，不代替历史 |
| 盒子温缓冲 | 整理后的历史点及写入/上传状态 | 等待本地保存和上传确认，容量有限 |
| 盒子本地文件 | 原始采样、整理后的历史及必要上传状态 | 断网排查、补传；重启恢复路线仍需补齐和验证 |
| 云端热缓冲 | 每盒最新上传快照 | 首页、设备当前详情 |
| 云端温缓冲 | 收到的待落库历史批次 | 后台批量处理，内存不是可靠永久存储 |
| 云端 MySQL | 历史点、测量、作业、轮次、恢复事实等 | 长期查询和后续统计依据 |

原始采样与整理历史是两种数据。正常 DOWN 不上传常规曲线，不等于禁止盒子保留原始 DOWN 采样。

盒子原始数据目标保留 3～4 天，云端保留期另行配置。未获保存确认的数据不能因普通过期清理静默删除；超过容量或保留能力时需要明确提示和处理策略，不能承诺无限断网不丢数据。

## 4. 从盒子到数据库的目标完整流程

```text
PLC 采样 → 清洗服务真实快照
  ├─ 热缓冲 → 定时实时上传
  └─ 历史整理 → 盒子温缓冲
       → 本地 DAO 保存成功
       → 生成稳定历史批次 → 命令服务上行消息队列
       → MQTT
       → 云端网络接入队列
       → MQTT 表示层转换、校验
       → 大厅 → 统计服务 → 云端历史温缓冲
       → 历史持久化任务 → DAO → MySQL 事务提交
       → 云端业务保存 ACK
       → 盒子校验 ACK、持久化确认状态、释放对应待上传缓存
```

实时快照更新不自动等于历史落库，也不应把所有实时帧重新存成常规历史点。

### 4.1 盒子本地保存

当前已有的代码顺序：

1. TelemetryService.reduceCycle() 整理输出。
2. BufferCenter.appendRoundRecord() 放入温缓冲。
3. CleaningPersistenceWorker.persistCycle() 调用 takePersistenceRecords()。
4. InnerWallCleaningDao.saveTelemetryRecord() 写入本地文件。
5. completePersistenceRecords(records, success) 标记结果。
6. takeUploadPending() 只取已经 persisted 且不在 inflight 的记录。
7. TelemetryService.uploadCycle() 组批，CommandService.enqueueHistory() 生成消息。

本地写失败，记录仍等待重试。入队失败时 returnUnsent() 解除 inflight，不删除历史。消息入队成功仅表示等待发送/确认，不代表云端保存完成。

当前本地保存先行约束已存在，但磁盘写成功的断电可靠性、未确认批次持久化和启动重建还需要专门验证。

### 4.2 云端接收

当前已有入口：

1. MqttService 收消息并放入接收缓冲。
2. CleaningMqttDispatcher.runDispatchCycle() 消费消息。
3. JacksonCleaningMqttInboundConverter.toHistory() 委托 CleaningMqttConverter.history() 转换。
4. CloudLobbyService.receiveHistoryBatch() 分发。
5. CloudStatisticsService.acceptHistoryBatch() 接收业务批次。
6. CloudWarmBuffer.offerHistory() 暂存。
7. TelemetryHistoryPersistenceTask 通过现有线程中心定期调用 runRealtimePersistenceCycle()。
8. 统计服务将 BO 转为 Entity，调用 TelemetryHistoryDao.insertBatch()。

现有转换直接返回 TelemetryBatchBo，不应描述成专用上传 DTO/Param 已经全部实现。后续按既有分层对齐外部 DTO 和内部参数，仍复用现有转换入口及业务对象。

### 4.3 云端事务保存

目标同一批次事务包含：

- 校验目标盒子、统一业务 ID、轮次归属、版本、单位和有效性。
- 检查稳定批次身份和内容指纹。
- 登记批次。
- 保存各历史记录及测量。
- 登记待发送保存确认状态。
- 全部成功后提交。

某点或某测量写失败，整个批次回滚；不能只保存批次头后回复成功。网络发布必须在事务提交后进行，不能将等待 MQTT 放进数据库事务。

当前 JdbcTelemetryHistoryDao 有批次、记录、测量同事务入口，但新增字段和内容冲突校验尚未接入。后续主要使用 MyBatis-Plus，保持 TelemetryHistoryDao 接口及业务调用，不新建平行存储链。

## 5. 业务保存确认与补传

QoS 1 的 Broker PUBACK 只代表 MQTT 传输确认，不代表 MySQL 提交。

目标保存确认使用共同协议草案中的批次身份、streamId、记录数量及明确记录序号集合；相关 Topic 和字段仍待双方实现，不能当作当前已可用。

- MySQL 未提交：不得回复保存成功。
- MySQL 已提交，ACK 未发出或丢失：保留待回复状态；盒子重传时核对原内容后重发确认。
- 同批次同内容：不重复插入、计数，可重复回复原保存结果。
- 同批次不同内容：拒绝并提示冲突，不用 INSERT IGNORE 掩盖。
- 同一源记录换批次上传：按稳定源身份校验并去重，避免唯一键冲突导致永远无法补传。
- ACK 必须匹配盒子、批次和真实记录集合，不能按最大序号无条件释放前面所有记录。

当前 confirmUploaded(throughSequence) 会处理范围内已落盘且 inflight 的记录。它不能直接拿某个批次的最大序号调用，否则乱序 ACK 或有空洞时可能误释放其他批次；后续需精确批次确认或证明连续确认范围。

盒子先持久化确认结果，再释放相应待上传温记录。本地历史文件继续按保留策略处理，不因收到 ACK 立即全部删除。未确认批次应保持身份和内容稳定，应用超时也需要补传，不能只靠 MQTT 自带重发。

## 6. 失败、重启与日志

| 情况 | 目标处理 |
|---|---|
| 本地写失败 | 保留未保存记录、重试；不进入上传 |
| 断网/发布失败 | 保留原批次和消息，恢复后重发 |
| 云端温缓冲满 | 不回复保存成功；明确容量问题，依赖盒子保留及业务重试 |
| 云端数据库失败 | 回滚并保留待处理批次；不要把接收成功当保存成功 |
| ACK 丢失 | 盒子重传，云端去重并重复回复 |
| 云端重启 | 内存队列可能丢失，依赖盒子未确认批次重新上传 |
| 盒子重启 | 从本地未确认历史和批次状态恢复，不能只恢复最新快照 |
| 历史先于轮次事件到达 | 保留历史事实，等待归属/终态核对，不直接宣布合格轮次 |

现有 CloudWarmBuffer 失败回队可能因生产者补满队列而抛错，当前不能宣称内存回队绝对不丢。后续要考虑在途容量预留或持久化待处理；最终恢复仍以盒子未确认批次为基础。

常规定时上传和正常写库可用 debug 或周期汇总。持续故障记录一次状态变化，恢复再记录一次；不要每 500ms 输出一次同样的错误。日志不写 accessCode、完整凭据和大量逐点 payload；面向用户的提示与内部诊断分开。

## 7. 从历史到页面

历史列表先查询 session，再关联完成轮数、结果和告警；具体轮次详情查询 round 与对应历史点。活动轮次可展示已保存真实点，但未完成不纳入已完成轮次统计。

正常参考曲线只使用合格自动轮次的 NORMAL_UP 点；异常/恢复另外展示。统计资格由轮次终态及完整性决定，不能由一个有效点决定。

后端提供曲线点、单位、坐标轴和轮次开始/结束时间，前端只展示。真实点平均仅能称“留点平均”，不等于全部 500ms 样本的时间平均；稀疏点最大值也不等于全程最大值。月、季度、半年、年及同比环比计算在后续统计阶段实现，不另建每页面一张表。
