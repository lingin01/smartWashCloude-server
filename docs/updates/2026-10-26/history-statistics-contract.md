# 实时、整轮历史与历史统计的统一口径

更新日期：2026-10-26。本文是讨论阶段的业务约定，不是已完成的代码或数据库迁移。最新主历史口径改为：**一次M106控制的自动运行过程对应一条主历史，由开始、结束边沿及约定的异常收尾确定边界**。四台动力设备及八个传感器都归属这一条主历史；上行、下行、回退、重试是轮内过程，提前异常结束也保留一条记录。

本页用于统一实时页面、历史列表、单次详情和日/月/季度/半年/年统计。先前“一次上行一条、另关联往返”的方案及其17张表DDL仍是前一版结构，后续需要按本页重新适配，不能把已有SQL验证解释为已经实现M106整轮识别。

## 1. 一条主历史如何开始与结束

| 情况 | 主历史处理 | 计次与结果 |
|---|---|---|
| 观察到自动轮次M106从0变为1 | 创建一条主历史，记录开始时间，重新建立本轮M60/M61观测累计 | 系统开始次数增加1，状态为进行中 |
| M106保持1，发生上行、下行、暂停、回退或重试上行 | 更新同一条主历史及轮内分段 | 不另增加开始次数，不提前写最终结果 |
| M106从1变为0，本轮M61曾为1 | 结束当前主历史 | 异常结束 |
| M106从1变为0，本轮M61未曾为1、M60曾为1 | 结束当前主历史 | 异常完成 |
| M106从1变为0，本轮M61、M60均未曾为1 | 结束当前主历史 | 正常完成 |
| 当前轮次中TCP连接断开，或PLC重启已得到确认 | 结束当前主历史，保存原因及观测到的结束时间 | 异常结束，不续接原轮次 |
| 检修运行 | 继续提供实时数据 | 不创建清洗主历史，不计入本页清洗历史统计 |

M61的优先级高于M60；即使两者在本轮都曾为1，最终仍是异常结束。“曾为1”是本轮内累计的事实，开始与结束边沿所在批次也要纳入；后续恢复为0不抹去此前事实，也不能把上一轮的累计带入下一轮。M60/M61用于结果分类，不单独触发一条新的主历史。

通信恢复后，即使第一次读到M106=1，也不把它当作新一轮开始，不把原轮重新打开。必须重新观察到0，再观察到下一次0→1，才能建立下一条主历史。系统首次接入时直接读到M106=1也遵循这个规则，不补造此前未观察到的开始边沿。PLC重启须有确认依据，不能单凭某个计数下降就猜测重启。

TCP断开采用连接层给出的中断事实，不增加逐字段“未知/未标定”等判断。连接断开或重启的结束时间记录本系统实际观测时间及原因，不声称已知PLC在断线期间的精确物理停止时刻；断线后未采到的测量不补造。已经结束的同一轮不能因重复通知再次计次或再次结算。

M204、D10～D13保留各自PLC事实，不再决定主历史的起止边界。D10～D13作为PLC累计值展示和追溯，不以今日末值减昨日末值生成日次数，也不据累计值反推遗漏的主历史。

## 2. 实时、历史和统计使用同一轮身份

| 数据入口或页面 | 统一含义 |
|---|---|
| 实时数据 | 当前成功采集的系统、四机和八传感器状态；自动、手动、检修均可实时展示 |
| 当前自动轮次 | M106开始边沿创建的主历史身份，以及本轮M60/M61累计、当前阶段和已累计摘要 |
| 历史列表一行 | 同一轮从开始到结束的主历史；进行中的一行显示“进行中”，结束后显示三种结果之一 |
| 单次详情 | 主历史起止、结果、轮内过程、各机上行高度点、全UP采集流摘要及关联事件 |
| 历史统计 | 从这些主历史的开始/结果事实和分日测量摘要计算，不另建一套“次数判断” |

一个系统的一轮只计1次，不因有四台动力设备就计4次。单机视图可以展示该设备在所属轮次中的运动和测量，但四台的参与数量不能相加作为系统轮次。

同一轮内回退后再次上行，仍使用原主历史身份；各次连续UP过程用轮内分段区分。再次经过相同高度可以保留新的实际测量点，不能用高度唯一键覆盖前一次，也不能据此新增主历史次数。

## 3. 次数、已结束结果与进行中分别统计

以下名称是业务字段约定，尚不是对现有SQL字段的声明。日历周期默认按主历史的**开始时间**选取该周期开始的轮次，并以查询时已知结果统计。

| 业务字段 | 中文含义 | 计算规则 |
|---|---|---|
| `started_count` | 开始次数 | 开始时间落在所选周期内的主历史数 |
| `normal_completed_count` | 正常完成次数 | 上述主历史中，最终结果为正常完成的数量 |
| `abnormal_completed_count` | 异常完成次数 | 上述主历史中，最终结果为异常完成的数量 |
| `abnormal_ended_count` | 异常结束次数 | 上述主历史中，最终结果为异常结束的数量，包含连接中断/已确认PLC重启导致的结束 |
| `finished_count` | 已结束次数 | 三种最终结果次数之和 |
| `completed_count` | 完成次数 | 正常完成次数＋异常完成次数；异常结束不算完成 |
| `running_count` | 该周期开始且仍进行中的次数 | 上述主历史中尚未结算最终结果的数量 |

在已记录轮次的同一统计版本、同一开始时间范围内，应满足：

```text
started_count = finished_count + running_count
finished_count = normal_completed_count + abnormal_completed_count + abnormal_ended_count
completed_count = normal_completed_count + abnormal_completed_count
```

进行中不能先计入正常完成，不能因为暂时没有异常信号就提前算成功。结束后更新开始日的结果分布，开始次数保持不变；同一最终结果重放或重算不重复累加。

`running_count`是所选周期内开始的轮次状态。实时页面的“系统当前是否运行”是另一个值，例如`current_running`：某轮昨晚开始、今天凌晨仍运行时，今日日报可以是`started_count=0、running_count=0`，但实时`current_running=true`。不能把这两个范围混用。

如果页面以后需要“今天实际结束了几轮”，须另设按结束时间统计的指标并注明日期依据，不能替换本页按开始日归属的结果次数。

## 4. 日、月、季度、半年和年如何展示

业务时区统一为`Asia/Shanghai`。时间点保存及传递应保留明确时区语义，数据库UTC时间先转换成上海业务日历再划分日期。周期采用左闭右开区间：包含起点，不包含下一周期起点。

| 周期 | 自然边界 | 建议呈现 |
|---|---|---|
| 日 `DAY` | 当日00:00至次日00:00 | 当日开始次数、三种结果、进行中，以及当日实际时长/测量；可列本日开始的主历史 |
| 月 `MONTH` | 每月1日至次月1日 | 按日展示次数、结果及实际分日摘要 |
| 季度 `QUARTER` | 1～3、4～6、7～9、10～12月 | 按月展示，可下钻到日 |
| 半年 `HALF_YEAR` | 1～6月、7～12月 | 按月展示，可下钻到日 |
| 年 `YEAR` | 当年1月1日至次年1月1日 | 按月或季度展示，可下钻 |

月、季、半年、年沿用相同含义：开始次数及结果归所属开始周期；时长和测量归实际发生的日期，再合并为所选周期。一次跨年轮次的结果仍回写其开始年份，不再算作结束年份开始的一轮。

跨日结束时，需要更新开始日及其上级月/季/半年/年结果；跨日采样则更新采样日及对应上级周期。已经过去的日期仍可能因跨日结算或可靠重放而更新，结果应有统计版本和已统计到的时间说明。合并高层周期时只选一组不重叠来源，不能同时加日汇总和已经包含这些日的月汇总。

## 5. 整轮总历时与UP运动时长按实际日期拆分

| 时间指标 | 区间来源 | 跨日处理 |
|---|---|---|
| 整轮总历时 | 主历史开始至结束的已确认区间；进行中暂计至本次统计时刻 | 与上海各自然日求交集，分别累计 |
| 单机UP运动时长 | 本轮内该机实际UP的连续运动区间 | 按该机实际区间分日拆分，不包含停止、DOWN和检修 |
| 系统上行窗口历时 | 当前已建立的自动轮次中，M106活动且任一台实际UP的区间 | 多台同时UP的重叠时间只计一次，按区间分日拆分 |

整轮总历时包含本轮内的上行、下行、暂停和回退等过程，不能用D16或D66～D69一次读数直接替代；这些PLC原值仍可保留和核对。四台UP运动时长可以作为四个设备指标；如果另展示其总和，应明确叫“设备UP运动累计时长”，不能叫系统整轮总历时。

以轮次在**10月26日23:58开始，10月27日00:04正常结束**为例：

| 指标 | 10月26日 | 10月27日 |
|---|---:|---:|
| 开始次数 | 1 | 0 |
| 正常完成次数，结束后回写 | 1 | 0 |
| 该轮贡献的整轮总历时 | 2分钟 | 4分钟 |

在10月27日00:01查询时，该轮尚未结束：10月26日的开始次数为1、进行中为1、三种最终结果均为0；实时页面仍显示正在运行。00:04结束后，更新10月26日为正常完成1、进行中0，不能给10月27日再增加一次。

若该机实际UP区间为23:58:30～00:00:30，则该机UP运动时长分别为10月26日90秒、10月27日30秒。测量按每条真实采集时间所属日期分配，午夜处不插值制造新的高度或拉力测量。

## 6. 全UP采集流用于统计，0.5m点用于历史曲线

0.5m限定长期曲线留点，不限定统计来源。每台在本轮实际UP期间的**每批成功采集**都参与本机测量摘要，包括上行重试段；即使该批没有被选为0.5m历史点，也应累计。正常DOWN不保存连续曲线，不进入UP测量统计。必要轮次边界和异常事件事实仍独立保留。

| 测量对象 | 来源与运算 | 需要保留的摘要 |
|---|---|---|
| 每个传感器拉力 | 对应实际采集及换算值 | `sum/count/min/max`、极值时间及该机当时实际高度 |
| 每台总拉力 | 同一批该机两个传感器拉力相加 | 对每批之和累计`sum/count/min/max`，保留极值时间/高度 |
| 每台速度 | 本机UP采集流的实际计算值 | `sum/count/min/max`、极值时间/高度；单位随结果明确返回 |
| 电机转矩等效力 | 本机原始转矩按确认公式换算 | 单独的`sum/count/min/max`及极值时间/高度，不混入绳索总拉力 |
| 系统总拉力 | 系统上行窗口内，同一采集批次八个传感器拉力相加 | 每批只累计一次，保留极值时间及四机当时高度 |

系统峰值必须先逐批求八传感器总和，再求总和的最大值；不能把四台或八传感器各自在不同时刻出现的峰值相加。某台触发一个0.5m点时，保存的其他设备同批上下文可以解释当时系统总力，但不能自动变成其他设备的高度点。

本次整理统一采用**系统上行窗口**：当前已建立且未结束的自动主历史内，M106活动，并且任一台实际UP，该批就纳入系统总力统计。四机方向不同步时，其他设备可能DOWN或停止，其同批传感器读数仍是八索总力的组成部分，但不因此进入那些设备各自的UP均值或UP运动时长。单机始终只纳入本机实际UP流。同一主历史中的同一系统批次只累计一次，八个值必须来自同一采集批次；不使用尚未明确完整枚举的D202另行定义系统UP阶段。

单次摘要覆盖本轮所有符合条件的UP段；分日摘要按实际采集日累计。月/季/半年/年均值使用各来源的`sum`之和除以`count`之和，不能平均每天的均值，也不能把每轮均值不加权地平均。例如第一天2条均值100kg、第二天8条均值200kg，合并均值为`(2×100+8×200)/10=180kg`，不是150kg。这是采样均值，不声称是时间加权均值。

各测量分别保留自身数量；没有采样时不把均值或极值写成0。统计量、极值时刻及高度需要在采集过程中可靠、分批保存，不能仅在内存累计至结束。当前未长期保留的全流原始帧，后续不能从稀疏高度点精确重算新的全流口径。

## 7. 0.5m点、高度桶与上行重试

每台分别按自己的高度到达或跨过0.5m目标节点时，保留之后取得的第一条真实测量，并区分目标高度和实际高度。例如目标0.50m、实际采到0.52m，就保存0.52m，不插值改成0.50m。必要起止、异常和极值事实可增加点数。

同一主历史内发生退回、重试上行时，保留所属UP分段身份、实际时间和选点原因。再次经过同一高度的点可以并存：它们解释的是同一轮的不同过程，不代表又完成一次清洗。各机是否被选作高度点必须独立标记；四机批次宽表中附带的其他设备读数不直接扩展成其连续曲线。

高度桶用于把**已经保存的高度点**分组生成跨轮高度曲线，须明确统计来源为已保存点。它的样本数量、均值和峰值不能冒充全UP采集流摘要。全流峰值可能发生在两个0.5m点之间，因此“高度曲线最大值”和“全UP采集峰值”可以不同，页面和导出应显示各自来源。

重试会增加同轮点数和全UP采样数。若后续需要“每轮在每个高度仅贡献一个值”来比较跨轮曲线，必须另外定义分段与重试选择规则，不能悄悄覆盖原点或把重复经过当作新轮次。

## 8. 故障事件数与受影响轮次不是同一个次数

D3=50等故障可能在某轮开始前已经存在，持续跨越多轮。事件以一次真实开始、持续和结束形成稳定事件身份；新一轮开始、同码持续或事件状态更新，都不另制造一个故障起点。

一条故障事件可以关联多条受影响主历史，一条主历史也可以关联多条事件。例如一个D3=50事件从10:00持续到11:00，期间轮次A、B都受影响，应为“故障发生1次、受影响轮次2次”，不是故障发生2次。事件结束后再次真正发生，才建立新的事件。

故障发生次数按事件实际发生或首次观测日归属；跨日持续时不因每日统计而重新计为新发生。受影响轮次按本页主历史开始日归属。关联事件用于解释原因，不用D3码自行替代M106边界或M60/M61结果分类，也不由D3=50补造若干次重试记录。

现有仅一个`record_id/cycle_id`的事件主关联不能完整表达“一事件影响多轮”。后续结构适配时须补足可追溯的多轮关联方式，而不是复制事件并造成故障次数增加；本文不实施表变更。

## 9. 后续数据库与业务接入的适配范围

当前[17表数据库说明](README.md)、[新增表定义](../../../src/main/resources/db/cleaning-v2-tables.sql)和[此前高度历史方案](../../database/height-history-period-capacity-20261025.md)保留为上一阶段成果。它们的上行/往返边界、结果与计数含义仍需适配本页新约定，不能直接沿用旧表名就认定业务语义已经一致。

| 后续适配项 | 需要达到的业务效果 |
|---|---|
| 主历史身份和状态 | 一轮一条，以M106边沿开始/结束；M60/M61按本轮累计；通信断开/确认重启结束且不续接 |
| UP过程与选点 | 同一主历史下多段、四机分别记录；0.5m选点和重试点不另增加主历史次数 |
| 日历次数和三类结果 | 明确开始日归属，区分开始、已结束、完成和进行中；结束后回写开始周期 |
| 分日时间和全流摘要 | 整轮总历时、单机UP运动与各测量按实际日期拆分，系统同批总力只累加一次 |
| 事件与轮次关联 | 一个跨轮事件可关联多个主历史，事件本身保持唯一 |
| 可靠保存与重算 | 同一来源重复提交不重复增加任何计数/统计；保存轮次检查点、摘要增量、留点及受影响周期，允许历史结果按版本更新 |

现有隔离MySQL验证证明的是前一版DDL、关联约束和人工构造数据的承载能力；没有证明自动识别M106整轮、M60/M61累计、0.5m选点或全流统计已经接入。本文没有修改SQL、Java代码、PLC或现场数据库。

后续实现验收至少应覆盖：正常整轮；M60异常完成；M61优先异常结束；轮内退回重试不增次；跨午夜及跨年结算；进行中不算成功；连接中断/确认重启后等待新的完整开始边沿；检修不生历史；同批八索总力与独立峰值相加的区别；全流统计与稀疏点统计的区别；跨轮持续事件去重；相同来源重放后的结果不变。
