# SmartWash 后端完整总结：接口、主体流程、实时、历史与统计

> 2026-10-27实施更新：当前代码已接通M106整轮、实时换算、19表保存、历史/五周期统计、严重告警、配置保存和导出。参见[当前实施与接口补充](../2026-10-27/backend-implementation.md)。下文原有“待实现/17表/10个已接通”等标注保留为此前设计或核对基线，不能作为当前完成度；参数PUT当前只保存平台版本，现场生效须有PLC依据。

更新日期：2026-10-26。核对基线：本仓库提交 ce12285 的代码、现有数据库脚本，以及本次对话最新确认的 PLC 点位和业务要求。

本文供后端开发、前端对接和 PLC 联调共同使用。当前范围是一个系统连接一台 PLC，PLC 下有四台动力设备，每台绑定两个拉力传感器，共八个传感器。后端直接通过 Modbus TCP 与 PLC 通信，提供页面接口、实时推送、远程命令和后续历史统计。

**最新业务主线：M106 从 0→1 开始一条系统运行记录，从 1→0 结束；本轮观测到的 M60、M61 决定结果。四台共用一条本轮主记录。历史上行曲线按统一高度每 0.5 米留点；日、月、季度、半年、年同时提供次数和高度曲线。**

当前已有新版页面 Controller、部分实时与命令能力、旧历史批次保存器，以及共 17 张表的建表/升级脚本。**M106 整轮识别、有序历史通道、新表自动保存和周期高度统计尚未接完整；不能把有接口、有表或能采集，等同于整套业务已经完成。**

## 1. 对外接口与前后端对接

### 1.1 通用规则

| 项目 | 统一说明 |
|---|---|
| 新页面前缀 | /api/command-center，下文用 C 表示 |
| 登录 | /api/auth；除登录与刷新外，新页面接口要求 Bearer 访问令牌 |
| 查询输入 | GET 使用查询参数；写入使用 JSON 请求体 |
| 身份 | 页面用 systemCode、winchCode、sensorCode；后端明确映射内部 deviceId、winchId、sensorId、ropeId |
| 操作者 | 来自已认证账号，不接受前端填写操作者身份作为授权依据 |
| 成功包装 | {code:200,message,data}；新页面 HTTP 202 表示已受理，包装中的 code 仍为 200 |
| 失败包装 | 对应 HTTP 状态及 {code,message,data:{errorCode}} |
| 测量单位 | 内部换算、现有旧接口和数据库主要为 kg、m、m/min；新页面拉力按 t 返回，除以 1000 |
| 时间 | 时间点保留明确时区；数据库新链路按 UTC 保存，业务日历按 Asia/Shanghai 划分 |
| 时间范围 | 历史时间区间采用左闭右开；不能擅自把结束时间再加一天 |
| 返回空值 | 新页面已有可空字段显式返回 null；有效的 0 必须保留 |
| 大曲线 | 有点数预算、概览/保存点模式和游标；前端隐藏曲线不改变底层统计 |

正常读到的点按配置直接换算，不新增逐点“没有读到、原值未知、尚未标定”等业务分类，也不因为采样时间早晚新增拒收规则。已有 DTO 中的 valid、quality、missingReason 等兼容字段需要在后续对齐时处理，不能把字段存在解释为本次新增了这些判断流程。

## 2. 主体流程与模块职责

### 2.1 PLC 数据进入系统

当前代码的数据路径为：

~~~text
ModbusTcpClient / ModbusTcpDevice 读取 PLC
→ PlcDeviceService 将采集结果写入缓冲
→ PlcDataIngress 主动取出
→ PlcDevicePresentation 转换输入
→ CleaningLobbyService 接收设备事实
→ CleaningService 更新当前业务快照
→ CleaningStatisticsService 累计现有 PROCESS 统计
~~~

目标流程在这个基础上补齐历史，不另建一套绕过服务的采集系统：

~~~mermaid
flowchart TD
    PLC[PLC D区和M区] --> IO[通信采集任务]
    IO --> Q[按系统有序的采集与连接事件队列]
    Q --> BIZ[运行识别与数据换算]
    BIZ --> RT[最新实时缓存]
    RT --> PUSH[首页查询与实时推送]
    BIZ --> RUN[M106本轮状态与0.5米留点]
    RUN --> PENDING[历史待保存队列]
    PENDING --> SAVE[历史事务保存任务]
    SAVE --> DB[(主记录 保存点 摘要 事件)]
    DB --> STATS[周期统计任务]
    STATS --> PERIOD[(次数统计和高度统计)]
    PERIOD --> API[历史统计 图表 导出接口]
~~~

### 2.2 前端查询数据

~~~text
Controller 绑定请求
→ Web 表示层解析公开编号和返回结构
→ 大厅入口
→ 安全服务检查账号权限和系统归属
→ 清洗/统计服务查询缓存或数据库
→ 转为页面 VO 返回
~~~

实时读取最新缓存；历史读取已经保存的记录；周期图读取统计结果。查询本身不重新向 PLC 逐点采集，也不触发一条新的运行记录。

### 2.3 前端远程操作

~~~text
前端提交意图与 requestId
→ Controller/表示层
→ 大厅和安全检查
→ 清洗服务组织业务请求
→ 命令服务登记、去重、编码、排队
→ 同一 PLC 通信任务执行写入
→ 应答进入结果缓冲
→ 上层接入任务分发
→ 命令服务更新回执
→ 页面查询命令，实际设备状态继续取自 PLC 采集
~~~

### 2.4 一个大厅与四个业务服务

| 模块 | 职责 | 本次需要补齐的部分 |
|---|---|---|
| CleaningLobbyService | 统一接收页面请求和设备事实，选择路径 | 保持入口，不在此加入 SQL 或状态算法 |
| CleaningService | 清洗业务编排、当前系统状态、操作申请 | 最新点表换算、M106 本轮识别和历史数据交付 |
| CleaningCommandService | 命令幂等、队列、应答、超时和状态 | 持久审计、参数保存与现场生效确认 |
| CleaningSafetyService | 账号、权限、操作边界 | 按真实现场配置补齐必要规则 |
| CleaningStatisticsService | 样本累计、历史保存和统计 | 新表保存、五种周期次数/高度统计、查询和导出 |

账号服务属于认证基础功能。Controller 不计算高度、拉力和运行结果；线程中心只运行登记的任务；数据库 DAO 不回调业务服务。

## 3. 对象、编号与数据归属

~~~text
系统 systemCode / system_id
└─ PLC deviceId / device_id
   ├─ 动力设备1 winchCode / winch_id → 传感器1、2
   ├─ 动力设备2 winchCode / winch_id → 传感器3、4
   ├─ 动力设备3 winchCode / winch_id → 传感器5、6
   └─ 动力设备4 winchCode / winch_id → 传感器7、8
~~~

| 标识 | 用途 |
|---|---|
| systemCode | 页面选择系统 |
| deviceId | 后端连接和采集某一 PLC |
| winchCode / winchId | 页面和内部标识一台动力设备 |
| sensorCode / sensorId / ropeId | 传感器公开身份、内部传感器和索位归属 |
| recordCode / 内部主记录 ID | 标识一次 M106 运行；四台设备、所有高度点和异常关联都指向这一轮 |
| captureId + sampleSeq | 标识采集来源和采集序号，用于去重和重放 |
| sampleKey | 页面读取一个已保存点的稳定键 |
| requestId / commandCode | 一次用户请求及后端命令身份，两者不能混用 |
| eventCode / taskCode | 一个异常过程及一个导出任务 |

当前新版页面通过 cleaning.page.systems 配置公开编号、设备绑定及 allowedUsernames。动力设备 groupNo=1～4，各自 ropeNo=1/2，需要明确配置，不根据数组位置或编号后缀猜归属。之后迁入正式档案表时，应统一身份来源。

## 4. PLC 通信与点位清单

### 4.1 通信约定

| 项目 | 当前结论 |
|---|---|
| 通信协议 | 后端作为客户端，通过 Modbus TCP 读取 PLC |
| PLC 地址 | 按现场网络配置，可使用同一局域网 |
| 端口 / Unit ID | 502 / 1；Unit ID 已确认 |
| 在线状态 | 从 TCP 通信层取得；连接中断表示与 PLC 的传输通道中断 |
| 同 PLC 读写 | 统一通信任务串行调度；急停在待执行任务中优先，正在进行的请求需有明确超时 |
| D/M 地址 | 现场标签与协议地址分别保存，核对对应型号映射；不能给 M 区自行套偏移 |
| 单次寄存器数量 | 当前设备默认读/写各最多 120 个，软件校验的协议上限分别 125/123 |
| 多寄存器数据 | 读取分块保持一个 DINT 完整，不把它拆开解释为两台数据 |

同一批数据可能由多个 D/M 请求组成，不保证恰好来自同一个 PLC 扫描瞬间。没有 PLC 时间戳时，开始、结束和采样时间表示后端观测时间。

### 4.2 系统、本轮和故障

| 点位 | 已确认含义 | 系统用途 |
|---|---|---|
| D201 | 1运行、2待机、3检修、4故障 | 当前系统状态 |
| D202 | 自动模式总方向；原说明“m201=1”，手动时不变化 | 保留原值与自动限定，完整枚举待确认 |
| M106 | 0→1 本轮自动运行开始，1→0 本轮结束 | 唯一主记录的起止来源 |
| M60 | 1 有异常 | 记住本轮曾发生异常 |
| M61 | 1 本轮异常结束，下一轮开始复位 | 记住本轮异常结束，结果优先于 M60 |
| M3 | 1 表示总故障 | 显示系统故障事实 |
| D3 | 故障原因码 | 说明原因，不替代 M106 结束 |
| D10/D11 | PLC 成功上行/下行累计次数 | PLC 累计展示 |
| D12/D13 | PLC 故障上行/下行累计次数，急停计入 | PLC 累计展示 |
| D300～D303 | 电机1～4使能 error ID | 故障明细 |
| D304～D307 | 电机1～4运行 error ID | 故障明细 |

D10～D13 不用于识别历史边界，也不通过相减生成每日运行次数。M204、早期 D16 方案不再作为当前历史边界或必需计时依据。

### 4.3 四台动力设备

| 设备 | 状态 | 上行/下行 | 编码器 DINT | 连续运行秒数 INT | 两路拉力原值 | 电机原值 INT |
|---|---|---|---|---|---|---|
| 1 | D203 | M120 / M121 | D53～D54 | D66 | D30 / D31 | D70 |
| 2 | D204 | M122 / M123 | D55～D56 | D67 | D32 / D33 | D71 |
| 3 | D205 | M124 / M125 | D57～D58 | D68 | D34 / D35 | D72 |
| 4 | D206 | M126 / M127 | D59～D60 | D69 | D36 / D37 | D73 |

本机状态 0待机、1运行、2故障。每台方向独立取自己的 M 位：上行位=1、下行位=0 为上行，反之为下行。两个位都为 0 表示没有上下行指示；都为 1 应保留冲突事实，不自行任选方向。

### 4.4 字序、底部值和高度范围

PLC 已把 D0/D1 的测试值设为 1234567890，即 0x499602D2，高字 18838、低字 722。现场读取后确认高低字顺序，编码器按有符号 DINT 还原。

每台底部编码器计数分别实测；用户还将提供统一的最低和最高高度。底部计数是高度换算参数，最低/最高高度是曲线和统计范围，两者含义不同；都不替代 M106 运行边界。

详细来源见[最新 PLC 点位契约](realtime-point-contract.md)和[Modbus TCP 报文核对](../../modbus-tcp-document-check-20261025.md)。

## 5. 实时数据与换算

### 5.1 拉力

~~~text
单传感器拉力 kg = (原值 - 10) × 0.001 × 101.9716
本机总拉力 kg = 本机传感器1 + 本机传感器2
系统瞬时总拉力 kg = 同一采集批次的八个传感器之和
页面 t = kg / 1000
~~~

拉力合计按已确认归属计算。两传感器平均值和八传感器平均值可以作为其他指标存在，但不代替总拉力。系统瞬时峰值先逐批求总力，再取最大值，不能相加四台在不同时刻出现的峰值。

### 5.2 电机力矩换算值

~~~text
电机等效拉力 kg =
    (D70/71/72/73 原值 × 0.35 × 163.0883 × 1.0)
    / (9.80665 × 0.16)
~~~

每台保留原值和换算值，名称明确为“电机力矩换算的等效拉力”。它与两路传感器拉力分别展示，不加入传感器总拉力。

### 5.3 编码器高度

~~~text
r = (本机编码器原值 - 本机底部计数) / 8192

r <= 12：
    高度 m = r × 1.043
12 < r <= 24：
    高度 m = 12.516 + (r - 12) × 1.1069
r > 24：
    高度 m = 25.7988 + (r - 24) × 1.171
~~~

四台各用自己的底部计数，使用同一分段公式。12 圈为 12.516 米，24 圈为 25.7988 米，分段连续。不能把分段高度直接配成一个固定线性倍率。

### 5.4 速度和运行时间

~~~text
同一连续运动段的区间速度 m/min =
    abs(本次高度 - 基准高度) / (本次轴运行秒数 - 基准秒数) × 60
~~~

D66～D69 是整数秒，停止后会重新计数。只有时间差大于 0 才能形成新的区间速度；同一秒内保留基准等待计时推进，不用 0 作除数。暂停重计、反向和新连续段需要重新建立基准，不能跨段相减。

整轮持续时间来自 M106 起止观测时刻；各机上行运动时长来自实际运动区间；轴连续秒数是计算依据之一。三个时间指标分别保存，不能用某台停后重计的最后秒数表示整轮时间。

### 5.5 实时缓存与页面

实时缓存每批更新系统状态、四台状态/方向、四个高度和速度、八路拉力、四台总拉力、系统总拉力、电机等效力、故障原因及采集时间。上行、下行和检修都可显示实时值。

旧转换器仍依赖部分旧字段，并以本机拉力平均值组织旧 VO；最新 D201/D203～D206、独立方向、编码器高度与轴计时速度需要继续适配。点位可以进入现场采集文件，不代表这些业务实时字段已经全部正确换算。

旧转换器还会把部分状态来源不足的情况映射为 OFFLINE；后续应按最新约定区分 TCP 连接事实与 D201 业务状态，不能因为旧状态字段缺少就宣称 TCP 已中断。

## 6. 一条历史记录的完整生命周期

### 6.1 开始、过程和结束

| 收到的事实 | 后端处理 |
|---|---|
| 已观察到 M106=0，之后变为 1，且不是检修 | 创建本轮主记录，分配唯一编号，保存开始时间、当次参数与换算配置 |
| M106 持续为 1 | 继续同一轮，按各机实际方向处理数据 |
| 本轮读到 M60=1 | 记住“本轮曾有异常”，之后恢复 0 也不清除 |
| 本轮读到 M61=1 | 记住“本轮异常结束”，之后恢复 0 也不清除 |
| 暂停、回退、调平、重试上行 | 属于本轮过程，可分连续段，不增加新的系统主记录 |
| M106 从 1→0 | 先纳入结束批次的 M60/M61，再记录结束时间和最终结果 |
| 活动记录期间 TCP 断开或已确认 PLC 重启 | 当前记录异常结束，保留已取得的数据 |
| 反复收到 M106=0 或重复提交结束任务 | 已结束的记录不重复结算、不重复计次 |

M60/M61 的累计事实只属于当前轮。新一轮开始时重建本轮累计，并纳入新一轮开始批次的值；后台不擅自向 PLC 写 0 清除这些位。

### 6.2 三种最终结果

| 优先级 | 条件 | 结果 |
|---|---|---|
| 1 | 本轮曾读到 M61=1，或因通信中断/已确认 PLC 重启收尾 | 异常结束 |
| 2 | M106 正常结束，无 M61，本轮曾读到 M60=1 | 异常完成 |
| 3 | M106 正常结束，本轮 M60/M61 均未出现 1 | 正常完成 |

进行中是记录状态，不提前归入任何完成结果。M3、D3 和驱动器 error ID 用于解释原因；D3 非 0 不一律结束本轮，尤其 D3=50 的持续告警和重试。

### 6.3 首次连接、恢复和重启

- 首次连接或重连时直接读到 M106=1，只提供实时，不把连接时刻当作本轮真实开始。
- 旧记录已经异常结束后不续接，等待观察到 0，再观察到下一次 0→1 才创建新记录。
- 当前没有活动记录时，断线或故障不会凭空创建一轮历史。
- 后端进程重启后，已经持久保存但仍标记进行中的旧记录，应按“后台重启导致采集过程终止”异常收尾，不继续拼接；这是后续恢复流程建议，结束时间需标明最后观测或恢复结算依据。
- 不能单凭某个计数下降猜测 PLC 重启。需要确认的重启依据另行现场核对。

### 6.4 检修与异常重试

检修只显示实时，不新建生产运行记录、不保存该检修过程的上行曲线，也不进入生产历史统计。

自动运行中的回退、调平和重试，只要属于当前 M106，就仍在本轮中，不因方向变化被误判为检修。若运行过程中切换为检修，活动记录如何收尾需要现场走一遍；建议异常结束并记录切换原因，不能直接把后续检修数据继续算成生产运行。

D3=50 的原说明涉及“五次尝试”“三次回原”“超过三轮”，这些是不同层级的 PLC 处理描述。后端按已提供的 M106/M60/M61 记录结果，不自行重建内部重试次数，也不因报警持续就拒绝下一轮记录。

## 7. 历史数据保存什么、如何按高度留点

### 7.1 四类数据各有用途

| 数据层 | 内容 | 保存目的 |
|---|---|---|
| 采集批次 | 实际读取的 D/M 点、顺序、观测时间、连接事实 | 实时处理、边沿判断和计算输入 |
| 本轮主记录 | 系统、开始/结束、结果、当次参数、配置与异常关系 | 历史列表和次数统计 |
| 上行保存点 | 每台统一高度节点对应的真实观测值，必要的起止/异常/极值点 | 历史详情和周期高度曲线 |
| 上行摘要与事件 | 全上行采集流摘要、分日时长、有限异常过程点 | 运行总结、日历统计和问题追溯 |

正式长期历史不要求把每个轮询批次全部保存。现场工具可以输出完整采集文件，但这种测试输出不等于生产数据库的长期留存策略。

### 7.2 一条主记录的内容

至少包括：本轮编号、系统身份、开始/结束观测时间、进行中/最终结果、结束原因、本轮是否出现 M60/M61、当次参数与配置版本、四机参与关系、上行摘要和异常事件关联。

四台设备的高度、速度、两路拉力、总拉力、电机等效力保存在本轮下。一次上行到 10 米后回退、重试、再上行，只要 M106 尚未结束，仍然是一条主记录。

### 7.3 统一高度与真实测量

用户后续提供统一最低高度 Hmin 和最高高度 Hmax。四台曲线以及日、月、季度、半年、年统计，使用同一组间隔为 0.5 米的目标高度节点。若上下限不是整步长，需要在配置中明确边界点处理，保存真实起止点，不伪造节点测量。

每台在上行到达或跨过目标节点后，选取实际读到的点：

~~~text
目标高度：10.00 m
实际采到：10.04 m

统计归组：10.00 m 节点
真实测量高度：10.04 m
~~~

目标节点用于对齐曲线，实际高度用于还原采集事实，不把 10.04 改成 10.00。采集跨过多个节点时，不用一条测量复制成多个假节点，也不插值补出未采到的数据。

任意一台触发留点时，可以保存这一批四台上下文，但要标明哪些设备本次真正触发高度留点。其他设备的上下文不能自动成为它们在同一目标高度的留点。

同一轮回退后再经过相同高度，可保留不同连续段和序号的点，不能用“本轮+高度”唯一键覆盖原始过程。

### 7.4 一个保存点的内容

| 范围 | 保存字段 |
|---|---|
| 来源 | 本轮编号、采集实例、序号、观测时间、连续段 |
| 系统 | D201、M106/M60/M61、系统故障码与相关上下文 |
| 每台状态 | 本机状态、上/下行位、实际方向 |
| 编码器 | 32 位原始计数、本机底部配置、实际高度、目标节点 |
| 计时/速度 | 轴连续秒数、计算依据、区间速度 |
| 传感器 | 两路原值、两路 kg 换算值、本机合计 |
| 电机 | INT 原值、力矩换算的等效拉力 |
| 合计 | 同一批八传感器总拉力，以及明确来源的系统上下文 |
| 留点原因 | 高度节点、起止、异常或极值等 |

保存基础原值是为追溯换算依据；曲线仍为稀疏保存点，不能声称可完整回放未长期保存的全部采集流。

### 7.5 上行、下行和摘要范围

上行按 0.5 米留点，同时用上行采集流累计摘要。正常下行提供实时值，并参与本轮生命周期，但当前方案不长期保存完整下行测量曲线；异常过程可留有限触发、峰值和结束点。

单机上行摘要只用本机实际 UP 数据。系统瞬时总力摘要在当前活动轮内、至少一台 UP 的采集窗口累计同批八路合计，每批只计一次。四台不同时上行时，不把系统总力摘要反推成各台的上行摘要。

全采集流摘要的最大值、最小值、平均值与 0.5 米高度曲线的结果可能不同。摘要累计 sum/count/min/max 及极值时间和高度，不能只拿稀疏点反算完整上行峰值。

## 8. 日、月、季度、半年、年如何统计

### 8.1 每个周期都提供两部分

| 部分 | 统计内容 |
|---|---|
| 次数与结果 | 总开始轮数、正常完成、异常完成、异常结束、已结束、已完成、进行中 |
| 按高度的测量 | 四台各自的两路拉力、本机总拉力、速度、电机等效力，以及四台/八传感器的高度对齐总拉力 |

月、季度、半年、年仍使用与单次相同的高度坐标，不仅仅返回“一个月多少次”。另外保留按日期展示次数变化的图或表。

### 8.2 次数定义

~~~text
开始轮数 = 已结束轮数 + 进行中轮数
已结束轮数 = 正常完成 + 异常完成 + 异常结束
已完成轮数 = 正常完成 + 异常完成
~~~

一次 M106 只计一个系统轮次，四台不是四次，回退重试也不另外增加次数。单机可以统计参与轮数，但不能相加后当作系统运行次数。

PLC 的 D10～D13 是另一组累计展示值，不要求与后端上线以来已保存的记录数量完全一致。

### 8.3 周期与展示粒度

所有自然周期按上海时区划分，区间左闭右开。

| 周期 | 数据范围 | 高度统计 | 次数变化展示 |
|---|---|---|---|
| 日 DAY | 当日 00:00 至次日 00:00 | 当天各轮在统一高度的数据 | 当天总数及结果；可查看逐轮 |
| 月 MONTH | 本月 1 日至下月 1 日 | 当月各轮在统一高度的数据 | 每天的次数 |
| 季度 QUARTER | 1～3、4～6、7～9、10～12 月 | 该季度各轮在统一高度的数据 | 每个月的次数 |
| 半年 HALF_YEAR | 1～6 月或 7～12 月 | 该半年各轮在统一高度的数据 | 每个月的次数 |
| 年 YEAR | 当年 1 月 1 日至下一年 1 月 1 日 | 全年各轮在统一高度的数据 | 每个月或每季度的次数 |

### 8.4 先整理一轮，再汇总多轮

周期高度曲线建议采用“每轮在每个高度贡献一份统计”的方式，避免某一轮因反复重试留点多，就在跨轮平均中占更大权重。

建议的计算顺序：

1. 按本轮、设备、来源和目标高度，把同一轮多次上行经过的已保存点归组。
2. 在轮内保留该高度的平均值、观测最大/最小值和点数；原始重复经过点继续保留。
3. 跨轮平均使用各轮该高度的代表平均值，每轮权重为 1。
4. 单机或单传感器的周期最大/最小值取参与轮次在该高度保存点中的实际极值，并注明来源为保存点。
5. 保留参与轮数、代表值合计、极值和规则版本，供更大周期合并。

这套轮内合并方式是建议口径，既有代码尚未实现；后续应与此前“保存点直接入桶”的方案统一，不能默默改统计含义。

例如 10 米节点有三轮本机合计拉力 1000、1100、1200 kg，则该周期该设备在 10 米的平均值为 1100 kg、最小 1000 kg、最大 1200 kg、参与 3 轮。此例只说明算法，不是现场数据。

### 8.5 两传感器、四台和八传感器的合计

~~~text
本轮、某高度、动力设备1总拉力 = 本机两传感器拉力合计
其他三台同样处理

本轮、某高度、系统高度对齐总拉力 =
    动力设备1总拉力
  + 动力设备2总拉力
  + 动力设备3总拉力
  + 动力设备4总拉力

周期、某高度的系统平均总拉力 =
    参与轮次在该高度的系统总拉力之和 / 参与轮数
~~~

系统高度合计必须先匹配同一轮、同一目标高度的四台数据，再跨轮统计。不能把各台来自不同轮次、不同样本集合的周期平均值直接拼成系统总力。

采用上述轮内代表平均值时，每轮系统高度合计由该轮四台在该节点的代表值相加得到。系统高度曲线的周期最大/最小值在这些“每轮高度合计值”中选择，不能把各台的独立极值相加；它也不叫同批瞬时峰值。

四台数据是在相同高度对齐时，可能来自不同采集时刻，所以“高度对齐总拉力”与第 5 节“同批瞬时总拉力”是两种统计来源。前者用于高度曲线，后者用于当时系统受力和瞬时峰值，名称与导出来源应区分。

### 8.6 异常记录和未到达的高度

建议周期高度曲线纳入已经结算的三种结果；异常结束只贡献实际采到的高度，进行中先在实时和当次详情展示，不提前当成完整周期参考轮次。是否需要按结果筛选，可沿用历史条件提供。

例如到 10 米异常结束，10.5 米以上没有测量，不能补 0 参与平均。各高度显示实际参与轮数。某一高度只有部分设备有点时保留单机数据，系统八传感器高度合计只使用该轮四台在此高度都具备数据的集合。

### 8.7 日期归属与跨日

已确定的次数口径是按本轮开始日归属。为让高度曲线对应同一组运行记录，本总结建议“按轮周期高度曲线”也按主记录开始日归属；这项高度曲线日期依据应写入统计规则，不与旧文档中按采集日拆分的全流摘要混用。

| 数据 | 日期依据 |
|---|---|
| 本轮开始及三种结果次数 | 本轮上海时区开始日 |
| 按轮周期高度曲线 | 建议采用本轮开始日，便于与次数和参考轮次一致 |
| 实际运动时长、全流测量摘要 | 按实际日期拆分 |
| 故障新发生次数 | 实际发生日；只有观测时间时明确使用首次观测日 |

例如 10 月 26 日 23:58 开始，27 日 00:04 结束：开始与结果仍归 26 日；本轮总历时 6 分钟，可按实际日期拆为 26 日 2 分钟、27 日 4 分钟。建议的按轮高度曲线整体归 26 日，按采集日的全流摘要则分别进入两日。

跨日或跨年结算后，要更新开始周期及其上级周期；实际日摘要分别更新对应日期。不会因跨零点多创建一条主记录。

### 8.8 合并统计和更新时机

- 保留合计与数量：均值=sum/count；轮均值、采样均值的分母分别保存。
- 月/季度/半年/年用相同口径加权合并，不能平均各日平均值。
- 最大值取参与集合中的最大值，最小值同理，不相加各设备的独立峰值。
- 同一次汇总只选一组不重叠来源，不能把日汇总和已经包含它们的月汇总再相加。
- 主记录或相关摘要成功保存后，标记受影响周期需要更新，由统计任务合并处理。
- 统计保留规则版本、请求/完成版本、统计到的时间；重试不能重复增加轮数。

如果修改底部值、高度范围或轮内取值规则，需要明确新版本和能否从现有保存点重算。未长期保存的全采集流不能事后凭空恢复。

## 9. 五类后台线程与队列

### 9.1 目标分工

本次确定先按 **5 个核心后台工作线程**安排。四机八传感器共用这套流程，线程中心统一管理生命周期。

| 工作线程 | 工作内容 | 初始调度建议 |
|---|---|---|
| 1. PLC 通信采集 | 读取整批 D/M 点、处理连接结果、消费远程写入队列 | 目标整批约 500ms，实际间隔现场测量 |
| 2. 有序业务处理 | 换算、更新缓存、M106 识别、M60/M61 累计、留点和摘要 | 按队列顺序处理，不做数据库或网络推送 |
| 3. 历史保存 | 主记录、保存点、摘要、事件和检查点的事务写入 | 普通过程点可 1～2s 批量提交，开始/结束及时触发 |
| 4. 实时推送 | 读取最新缓存并推送页面 | 新首页每秒一份完整视图 |
| 5. 周期统计 | 处理待更新周期，形成次数和统一高度统计 | 保存成功后触发，短时间内重复请求合并；可定时补偿 |

接口请求由 Web 容器处理，框架、数据库连接管理等还会有其他线程，所以整个 Java 进程不只 5 条线程。导出等后续耗时任务使用独立受限执行资源，不能长时间占用采集、有序处理或保存线程。

### 9.2 当前代码与目标的差别

| 现有登记任务 | 当前组织 |
|---|---|
| plc-device-io | PLC 开启时登记独立通信任务；工作检查默认 50ms |
| plc-device-dispatch | PLC 开启时登记独立分发任务，50ms |
| command-center-home-push | 新首页独立推送任务，每秒 |

ThreadCenter 当前有 2 条共享调度线程，并支持登记独立线程。兼容期还有新旧两套推送，因此“5 个核心线程”是后续目标分工，不是当前代码已经恰好运行 5 条线程。

### 9.3 三种缓冲各自的规则

| 缓冲 | 是否允许覆盖旧数据 | 原因 |
|---|---|---|
| 最新实时缓存 | 允许保留最新视图 | 页面关心当前值 |
| 有序采集/边界队列 | 不能把未处理批次静默覆盖 | M106 变化、M60/M61 和运动基准需要保持顺序 |
| 历史待保存队列 | 未提交任务不能丢弃 | 保存延迟不能混轮、漏结束或丢历史点 |

当前 PlcMessageBuffer 的 snapshots 按 deviceId 保存最新一帧，会覆盖前一帧。它适合实时展示合并，不能直接作为完整的历史识别通道。

连接断开、重连也应进入同一系统的有序处理路径，保证旧连接数据和新连接数据不会把异常结束的记录重新打开。队列有容量限制，满时要记录错误并采用明确的待写暂存/降载策略，不能继续覆盖后还声称历史完整。

### 9.4 采集频率和信号保持

最快 10m/min 时，经过 0.5m 约需 3 秒。完整采集批次以约 500ms 为初始目标，可取得多次观测，但要实测多块请求、网络和超时后的实际最大间隔。

有序队列只能保证已经采到的信号不被后端覆盖。M61 等信号的保持时间仍需覆盖实际读取间隔；若 PLC 在两次读取之间完成整个脉冲，线程安排无法补回未采到的变化。

### 9.5 开始、结束和停止服务

开始任务先于本轮点，结束任务位于本轮最后点之后。所谓“结束及时保存”是立即唤醒保存器处理此前任务，不能让结束任务越过尚未保存的点。

正常停止服务时，建议先停止新采集、处理已接收数据、提交或持久暂存待写任务，再关闭数据库和线程。当前 ThreadCenter 的停止主要是取消任务与中断等待，并没有自动完成新的历史队列排空流程，后续需要接入。

线程依据：[ThreadCenter](../../../src/main/java/com/company/project/info/thread/core/ThreadCenter.java)、[PLC 接入任务](../../../src/main/java/com/company/project/presentation/plc/PlcDataIngress.java)、[首页推送](../../../src/main/java/com/company/project/presentation/web/HomeStreamPresentation.java)。

### 10.3 保存事务建议

~~~text
一批输入或保存任务
→ 核对来源和本轮归属
→ 写入主记录开始/更新
→ 写入本批保存点
→ 更新对应全流摘要和事件
→ 最后一批时写最终结果
→ 更新已处理来源检查点
→ 标记受影响统计周期
→ 提交事务
~~~

批次保存，不把整轮所有数据放在一个持续数分钟的长事务里。唯一键沿用原始采集来源和序号，重放不会重复计数；同一高度重复经过的点仍可共存。

### 11.2 请求、应答与实际执行


## 12. 故障、异常事件和日志

### 12.1 故障原因字典

| D3 | 含义与归属 |
|---|---|
| 0 | 当前无故障码，不抹去本轮已记住的异常 |
| 10～13 | 电机1～4使能故障，结合 D300～D303 |
| 15～18 | 电机1～4运行故障，结合 D304～D307 |
| 20～27 | 拉力1～8异常，可能涉及绳、连接或拉不动 |
| 28～35 | 拉力传感器1～8故障 |
| 40～43 | 编码器1～4读数异常 |
| 50 | 无法移动、回退/调平重试及跨轮持续告警，保留 PLC 原说明 |

error ID 具体码义由驱动器错误表解释；没有依据不自行给等级或保护类型。单个 D3 当前码也不能自动提供所有并发故障。

### 12.2 事件与运行记录的关系

持续异常形成一个稳定事件，反复读到相同故障不每次新增一条。一个事件可影响多轮，每轮保留与它的关联。

例如 D3=50 连续影响三轮：故障新发生可只计 1 次，受影响轮次可以是 3 轮；各轮结果分别由自己的 M60/M61 判断。故障恢复与本轮结束分别记录，不能把“本轮结束”自动当作“持续故障解除”。

当前未提供完整的事件编号、所有并发故障和等级协议，后端可整理明确观测到的过程，但不能承诺已经掌握 PLC 内部所有事件和精确切换时刻。

### 12.3 三类日志与统计分工

| 内容 | 保存位置与用途 |
|---|---|
| 运行次数、拉力/速度/等效力统计 | 主记录、摘要和周期统计表，供页面查询 |
| PLC 故障、连接中断及有限现场点 | 事件及关联结构，供历史追溯 |
| 远程急停/参数/阈值操作 | 持久审计，供操作追责和结果查询 |
| 程序错误、任务失败、统计重建结果 | 应用日志，按文件策略滚动保留 |

统计任务可以记录执行范围、版本、处理数量和耗时，但日志不是运行统计的唯一数据源。每个采集点也不必逐条打印到应用日志。

## 15. 一年数据量与保存策略

用户提供的工况是单次上行约 25～27 米、最快 10m/min、设置间隔最短约 30 分钟、数据库磁盘约 1.5TB。实际统一最低/最高高度仍以后续提供为准。

以最低 0 米、终点也保留、行程 25～27 米为估算示例：

~~~text
每台每轮基础高度点：约 51～55 个
四台每轮逻辑高度点：约 204～220 个

仅取 48 轮/日作为容量场景：
每年四台逻辑点数约 357 万～385 万个
~~~

48 轮/日是按 24 小时和 30 分钟作的估算场景，不是已确认生产次数上限；实际还受运行时间、间隔从何时起算、停机和异常影响。

若四台同批触发，共享一行四机采样会减少物理行数；不同步、回退重试、异常和极值留点会增加行数。不能直接把逻辑点数当成某张表的最终行数。

按每行含索引约 1KiB 的粗略场景，基础采样表可在每年约 1～4GB 量级；实际宽行、索引、JSON 和事件量需要用代表性数据实测。1.5TB 的规划同时考虑数据库数据、索引、binlog、日志、导出、备份和空闲空间，不能据这个粗算承诺能使用多少年。

当前不为每种周期复制全部原始点，也不增加按天分表或自动删除生产数据。长时间保存上行留点及摘要；旧数据归档、保留年限和导出文件过期策略按实际增长再定。

### 16.2 新主流程必须覆盖的场景

| 场景 | 预期 |
|---|---|
| 正常开始、上行、下行、结束 | 只有一条正常完成记录 |
| M60=1 后恢复 0，最后正常结束 | 一条异常完成记录 |
| M61=1，结束时已回 0 | 因本轮累计事实仍为异常结束 |
| M60/M61 同时出现 | 异常结束优先 |
| 结束批次才读到 M61 | 先记异常，再结算 |
| 回退、调平、重试和同高度再次经过 | 主记录不增加，过程点不覆盖 |
| D3=50 持续跨轮 | 事件不每轮复制，主记录仍按每次 M106 新开始建立 |
| 运行中断线、恢复时 M106=1 | 原记录异常结束，不续接，等待下一次完整开始 |
| 首次接入 M106=1 | 只有实时，不伪造开始 |
| 检修运动 | 只有实时，不计生产历史 |
| 跨日、跨月、跨年 | 次数和结果按开始周期；实际日摘要按发生日期拆分 |
| 采到 10.04 米、目标为 10 米 | 保留实际高度，不补造 10.00 测量 |
| 途中异常结束 | 上方未到达高度不补 0，参与轮数准确 |
| 四机同高度集合不齐 | 单机数据可查，系统高度总力不拼凑 |
| 日均值样本/轮数不同 | 按合计和数量加权，不平均日均值 |
| 保存失败、重放、重复结束 | 不丢未提交任务，不重复点和次数 |
| 同一批次被多个用途引用 | 来源唯一，系统总力只累计一次 |
| 后台停止或重启 | 已保存数据保留；待写恢复与旧轮异常收尾可追溯 |

线程和保存可靠性应通过故障注入验证：数据库短时失败、队列积压、重复输入、异常位复位、断线重连和保存器重试。对比最终数据库记录与输入序列，确认开始、点、结束和统计完全对应。
