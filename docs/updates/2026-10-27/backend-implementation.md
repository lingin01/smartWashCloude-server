# 后端主流程实施与部署说明

更新：2026-10-27。本文记录本次代码实施结果；上一日《后端完整总结》保留为需求和设计基线，其“待实现”标注不再表示当前代码状态。

## 1. 已接通的主体流程

```text
PLC Modbus TCP读取
  → 原始值＋工程值解码
  → 有界、按序采集队列
  → 表示层 → 大厅 → 清洗业务
  → D201状态、四机独立方向、分段高度、轴计时速度、八路拉力
  → 更新实时快照 → 首页与SSE
  → M106整轮识别、M60/M61锁存、上行留点、故障事件
  → 本地持久待写文件
  → MySQL事务：主记录、留点、单轮/分日摘要、事件关联、输入检查点
  → 日统计 → 月/季度/半年/年统计
  → 历史查询、按高度比较、归档比较、后台导出
```

清洗服务负责运行识别与换算，命令服务负责操作生命周期，统计服务负责保存、查询、汇总和导出，安全服务负责权限；Controller只处理请求和返回。

## 2. 实时数据

- D201映射运行、待机、检修、故障。四台设备分别读取D203～D206、M120～M127，手动/检修时不依赖D202推断方向。
- 编码器保留有符号32位原值。配置本机底部计数后，使用已确认的三段卷筒公式算米；共用最低、最高高度，不以四机平均高度冒充圆环真实高度。
- 速度使用同一连续方向段的高度差、D66～D69秒计时差计算；停止、反向、计时回零后重新建立基线，不除以零。
- 网络层只换算一次。每台总拉力为两个传感器之和；系统实时总拉力为同一采集批次八个传感器之和。电机等效拉力单独保留。
- 首页增加`totalTension`，每台增加`totalTension/currentHeight/torqueForce`；页面力单位为t，内部及数据库为kg。
- `plcValues`保留已读到的M106/M60/M61、D201/D202、D3和D10～D13累计值。累计值不参与历史边界和平台计次。
- `captureId + sequence`用于标识当前采集实例和批次。采样时间不会因“超过有效期”被清空或排除。
- TCP断连后通信为离线；最后确认处于检修时，主状态继续为检修。后台重启也保留这一规则，首次重新连接前不会把旧运行状态显示为在线。
- PLC未连接不阻止后台启动，沿用后台自动重连机制。

尚未配置底部计数时，高度没有可计算值；这不影响保留编码器原值。没有读回点位的现场参数不显示为“已生效”。

## 3. 一次历史记录

一个系统的一轮M106只有一条主记录，四台动力设备共同关联该记录。

| 条件 | 处理 |
|---|---|
| 已经观察到M106=0，再观察到0→1 | 创建记录，记录实际观测开始时间 |
| M106=1期间 | 接收实时数据，上行按统一0.5m节点留点，累计全流摘要 |
| 观察到M60=1 | 本轮异常标记保持到结算 |
| 观察到M61=1 | 本轮异常结束标记保持到结算 |
| M106 1→0 | 先处理该批异常位，再结束记录 |
| 曾有M61=1 | 异常结束 `ABNORMAL_ENDED` |
| 无M61，曾有M60=1 | 异常完成 `ABNORMAL_COMPLETED` |
| 两者均无 | 正常完成 `NORMAL_COMPLETED` |
| 运行中TCP断连、切入检修 | 异常结束 |
| 后台重启遗留运行记录 | 在最后观测时间结束，原因为`BACKEND_RESTART` |
| 首次接入/恢复时M106已为1 | 仅实时，不补造开始；先等0，再识别下一次上升沿 |

检修不建立生产历史。D3=50等严重告警可以跨轮持续，不因“严重”级别自行结束记录。M204和D10变化不作为开始/结束条件。

每个留点保存同一批次四台的原值和换算值，并标明哪台触发留点。`height`为目标节点，`actualHeight`为实际测得高度；不会插值，也不会拿一条测量补齐多个跳过的节点。重复上行段保留各自段号。

上行全流摘要与0.5m曲线分开：摘要的极值、平均、采样数不由页面抽样点反推。系统同批总拉力的极值保存四台当时高度和批次来源。

## 4. 五种周期统计

DAY、MONTH、QUARTER、HALF_YEAR、YEAR都提供次数和高度曲线。

- 次数按本轮开始所在的上海自然日归属；四台不会重复累加四次。正常完成、异常完成、异常结束、进行中分别计数。
- 全流测量和观测运行时长按实际发生日期拆分，跨午夜不把次日测量全部归入前日。
- 日曲线按同一轮、同一设备、同一高度节点先归并，再让每轮等权参与周期平均。
- 八传感器高度对齐总力只采用同轮、同目标高度齐备的四台总拉力。不同设备可以在不同时间经过同一高度，该曲线与实时同批总力含义不同。
- 异常结束只贡献实际到达的高度，未到达的高度不补0。进行中的轮次不进入已结束轮次的周期高度参考。
- 长周期合并不重叠日报的`sum/count`，不平均各日报平均值。
- 统计任务按版本替换结果；新输入与统计重建并发时会保持待重建标记。
- 单机运行时长当前口径为“观测到的上行方向区间”；速度使用PLC轴秒计时。不会把该时长标称为PLC累计运行时长。

## 5. 接口

新版接口保留原有路由。除了登录和刷新，均需Bearer令牌；页面系统、动力设备、传感器和记录必须属于已授权系统。

| 入口 | 当前功能 |
|---|---|
| `/api/auth/login`、`refresh`、`user-info`、`logout` | 登录、刷新、账号信息、退出指引 |
| `/api/users` | 有权限账号查看用户 |
| `/api/command-center/home`、`home/stream` | 实时首页、SSE |
| `emergency-stop`、`commands/{commandCode}` | 受控急停申请、持久操作查询 |
| `winch/detail` | 单机实时、已保存/已生效配置、当日统计 |
| `winch/tension/trend` | 次数比较、日/月/季度/半年/年高度曲线 |
| `history/list`、`history/detail`、`history/point` | 历史列表、分页曲线、单批次四机读数 |
| `archive` | 按时间变化、独立区间比较、上一轮/历史参考高度比较 |
| `alarms/latest`、`alarms/history` | 严重PLC告警及归属 |
| `events/history`、`events/{eventCode}` | 异常事件、触发与结束快照 |
| `parameter-settings` GET/PUT | 平台参数读取与保存，保留现场生效版本 |
| `winch/tension-thresholds` PUT | 两个公开传感器的阈值保存 |
| `exports`及任务/文件接口 | 持久导出任务、查询与下载 |

表中命令中心相对地址统一以`/api/command-center`开头。输入字段及原路由详见[接口契约](../../external-api-contract.md)，本次增加/变化如下：

- `comparisonView`支持`COUNT/DAY/MONTH/QUARTER/HALF_YEAR/YEAR`；`periodStartDate`选择自然周期。
- `runResult`支持上述三种结果；兼容旧`COMPLETED`为两种完成，旧中止结果归异常结束。
- 曲线增加实际高度、最小/最大值、参与轮数、段号。详情`RAW`返回已保存点，`OVERVIEW`返回高度节点；RAW不表示把未保存的连续实时流重新生成。
- 详情额外返回每台两传感器总力、八传感器高度对齐总力、速度系列。时间及高度筛选同样作用于系统高度对齐曲线。
- 归档`WINCH_TENSION/TRACTION_ROPE_TENSION`继续对应传感器1/2，新增`TOTAL_TENSION`表示本机两传感器合计。前三种较长周期时间图按月分组；完整概要独立于分页点数。
- 归档“上一轮”默认只选同一上海自然日内、早于当前记录的已完成轮次；历史平均可提交独立参考日期范围，仍排除当前与后续记录。
- 所有日期范围按各接口明确的首尾包含规则处理；历史时间范围为左闭右开。
- 未启用正式历史时相关接口返回503。启用但暂无记录时返回空集合，不返回模拟数据。

## 6. 故障和操作审计

PLC故障全部为严重；提示级保留，不依据拉力数值在平台额外制造告警。事件给出系统/动力设备、故障码、部位和维修指向。D300～D307补充原码保存为`faultDetails`，不虚构驱动器错误码说明。

例如D3=28关联动力一号的传感器1；D3=41关联动力二号的编码器。钢绳拉力异常、电机使能/运行故障分别指向对应连接受力部位或电机/驱动器。持续故障保持同一个事件编号，可关联多轮。

远程操作先持久登记，再进入设备队列；应答先写入本地持久待写，再事务保存到审计表。数据库保存确认后才释放结果和命令缓存。数据库失败时保留结果；超时单独审计，不把超时当成发送成功，也不会自动重发不确定操作。

参数/阈值PUT按当前用户要求保存平台配置，返回`SAVED`、版本和可查询的操作编号；没有现场点位时也能保存。该保存入口目前不自动下发。既有受控写通道使用可配置地址、编码及开关；现场参数的实际读回与应用确认须在PLC补充定义后联调，不能仅凭写应答填`APPLIED`。

访问令牌默认30天、刷新凭据90天，可通过`jwt.expiration`和`jwt.refresh-expiration`配置毫秒数。修改配置只影响新签发凭据。退出沿用客户端清除令牌；未实现服务端逐令牌撤销。账号禁用及权限变化会在受保护请求中核对实际账号；旧管理员入口也要求实际管理员身份。

## 7. 后台任务

核心仍分为五类职责：PLC网络IO、有序业务处理、持久保存、实时推送、周期统计。IO不执行历史SQL；业务处理先追加持久待写；保存器用事务提交并确认检查点。

导出另用一个受限后台任务，按批读取和输出，避免占用实时采集；HTTP和框架线程不计入这五类核心职责。线程由统一后台任务中心登记、停止。

## 8. 数据库与升级

目前19表：16张目标/兼容表、3张原历史表。原`cleaning_cycle_record`继续兼容保留，新M106历史直接以`cleaning_run_record`为主记录，不再为同一轮生成第二套计次。

| 安装来源 | 执行文件 |
|---|---|
| 空数据库 | `src/main/resources/schema.sql` |
| 原7表device_id基线 | `docs/database/migrations/V20261026__upgrade_cleaning_v2.sql` |
| 上一版2026-10-26的17表 | `docs/database/migrations/V20261027__m106_runtime.sql` |

新增`cleaning_runtime_checkpoint`保存采集实例/序号检查点，`cleaning_event_run`关联持续异常与多轮。现有主记录、留点、事件、统计、导出表增加运行快照等字段。宽表也填入可直接查询的身份、原值、状态/方向、总力、极值及分日指标。

新表定义在`db/cleaning-v2-tables.sql`，原17表基线保存在`db/cleaning-v2-20261026-baseline.sql`供迁移生成和验证使用。运行`python tools/database/build_schema_v2.py`生成SQL，`--check`检查生成结果是否一致。

应用不自动执行迁移。升级前备份、停止应用写入，按实际基线选一个入口；不要混用空库脚本与升级脚本。历史摘要不会伪造成原始采样。实际业务数据库尚未改动。

## 9. 启用

迁移完成并确认公开系统映射后，在已有外部配置中设置：

```yaml
cleaning:
  history:
    runtime-enabled: true
    spool-directory: var/history-inbox
  exports:
    directory: var/exports
```

旧历史`persistence-enabled`与本流程独立；普通开发和测试默认不连接PLC、不启用新库写入。一个正式实例独占待写/导出目录；目录要持久保留，数据库重试依赖其中未确认文件。

`plc-points.example.yml`新增M106/M60/M61和D11～D13，仍全部默认禁用。四台底部计数配置在`encoder-bottom-counts`；统一范围为`height-min/height-max`。不要将模板中未确认的地址直接填成D/M标签数字。

## 10. 验证与现场边界

本次验证覆盖运行开始/结束、异常优先级、检修断连、首连M106已为1、重放幂等、持久待写恢复、事务回滚、跨日、加权统计、同高度齐备条件、操作审计后释放、归档分页以及真实CSV/ZIP导出。

实际数据库验证工具为`tools/database/verify_schema_v2.py`和`verify_runtime_flow.py`：只创建带所有者标记的临时MySQL，核对端口/目录后才写入，结束时清理临时实例。运行流程验证还会启动真实Spring服务并发起HTTP请求；没有接触现场PLC和业务数据库。

最终测试数量、构建结果及验证报告路径见[实施进度](implementation-progress.md)。

现场尚需提供：局域网IP、该PLC的M区/寄存器映射、32位字序、四台底部计数和统一高度范围。启动时刻/延时、间隔毫秒及速度写入/读回的完整编码仍需PLC明确。以上是现场配置与联调前提，不用假数据替代。
